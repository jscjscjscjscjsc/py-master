02. 17.1 为什么需要测试 ▼

17.1.1 概念认知：手工测试的局限

你之前的验证方式是什么？手动运行几次，看看输出对不对。问题是：

  • 改了一个函数，你怎么知道其他功能没被影响？（回归风险）
  • 下次修改时，你还会记得"当时怎么验证的"吗？
  • 边界情况（空列表、0 输入）你每次都测了吗？

自动化测试把"验证"写成代码：跑一次 pytest，所有用例自动验证。改完代码跑一遍，立刻知道有没有改坏——这就是"回归保障"。

17.1.2 概念认知：测试金字塔

       /\   端到端测试（少）：整个系统一起测
      /  \  （跑得慢、贵、脆弱）
     /----\
    / 集成 \ （中）：模块之间配合
   /--------\
  /  单元测试  \（多）：单个函数/类（快、便宜、精准）
 /______________\
  • 单元测试：测一个函数/类（本章重点）；
  • 集成测试：测模块之间的配合；
  • 端到端测试：模拟用户完整流程。

口诀：底层多、上层少——单元测试是地基，数量最多。

17.2.1 语法掌握：安装 pytest

17.2.2 语法掌握：第一个测试

代码案例 17.2：calc.py（被测函数，✅ 正确）

python
def add(a, b):
    return a + b

代码案例 17.3：test_calc.py（测试文件，✅ 正确）

python
from calc import add

def test_add():
    assert add(1, 2) == 3

def test_add_negative():
    assert add(-1, 1) == 0

约定（pytest 三大规则）：

  1. 测试文件名以 test_ 开头（test_calc.py）；
  2. 测试函数名以 test_ 开头（test_add）；
  3. 用 assert 表达式 判断——条件为假即测试失败。

17.2.3 语法掌握：运行 pytest

代码案例 17.4：运行测试（✅ 正确）

powershell
pytest -q

运行结果（全部通过）：

..                                                                      [100%]
2 passed in 0.02s

讲解：

  • 每个 . 表示一个通过的测试；
  • 2 passed in 0.02s：2 个用例全过、耗时 0.02 秒——以后每次改代码跑一遍，两秒内知道有没有改坏；
  • -q 是 quiet（简洁输出）。

交叉验证：测试失败长什么样

代码案例 17.5：故意写错的测试（❌ 演示）

python
def test_add_bug():
    assert add(2, 3) == 6      # 期望错了：2+3 应该是 5

运行结果：

.F                                                                      [100%]
================================== FAILURES ===================================
________________________________ test_add_bug _________________________________

    def test_add_bug():
>       assert add(2, 3) == 6
E       assert 5 == 6
E        +  where 5 = add(2, 3)

test_calc.py:7: AssertionError
=========================== short test summary info ===========================
FAILED test_calc.py::test_add_bug - assert 5 == 6
1 failed, 1 passed in 0.07s

讲解（读失败输出三步）：

  1. .F：第一个测试过、第二个挂（F = Failed）；
  2. E assert 5 == 6：断言详情——左边是实际值 5，右边是期望值 6；
  3. E + where 5 = add(2, 3)：pytest 告诉你 5 是从哪来的——不用你猜，它把"证据链"列出来了。

微任务卡（M1 · 报错卡 · L2）：故意写错一个测试，把 pytest 的失败输出发给 AI："请解释 assert 5 == 6 和 where 5 = add(2,3) 分别说明什么？"一句话记录理解。

原理探秘：pytest 是怎么"找到"你的测试的

pytest 启动时按约定递归收集测试项：文件名以 test_ 开头、函数名以 test_ 开头——收集到的每一个都成为一条"测试项"，逐个执行后汇总结果。pytest -q 里的 .（通过）和 F（失败）就是收集结果的图形化。理解了"收集机制"，就理解了为什么命名约定是硬规则——名字不对，测试根本不会被运行。

17.2.4 语法掌握：边界用例设计

好的测试不只看"正常情况"，还看边界。以第 7 章的 is_prime 为例：

代码案例 17.6：完整测试集（✅ 正确）

python
from calc import is_prime

def test_prime_normal():
    assert is_prime(97) is True
    assert is_prime(91) is False

def test_prime_edge():
    assert is_prime(0) is False     # 边界：小于 2
    assert is_prime(1) is False     # 边界：1
    assert is_prime(2) is True      # 边界：最小素数

def test_prime_big():
    assert is_prime(101) is True

讲解：

  • 正常用例：97（素数）、91（非素数，7×13）；
  • 边界用例：0、1、2——最容易出 bug 的地方就是边界（第 3 章 >= vs > 的教训）；
  • 用例分函数：一个测试函数测一类情况，失败时定位更精准。

17.2.5 了解：fixture——准备"测试材料"

多个测试需要同一份数据时，用 @pytest.fixture 准备：

代码案例 17.7：fixture（✅ 正确，了解级）

python
import pytest
from calc import calc_stats

@pytest.fixture
def sample_scores():
    """每个测试自动拿到一份成绩列表"""
    return [88, 92, 76]

def test_total(sample_scores):
    stats = calc_stats(sample_scores)
    assert stats["total"] == 256

def test_avg(sample_scores):
    stats = calc_stats(sample_scores)
    assert stats["avg"] == pytest.approx(85.33, abs=0.01)

运行结果：

..                                                                      [100%]
2 passed in 0.01s

讲解：

  • 函数参数写 sample_scores，pytest 自动调用 fixture 并把返回值传进来；
  • pytest.approx(85.33, abs=0.01)：浮点比较用"近似"（第 2 章 0.1+0.2 教训的正式解法）；
  • fixture 的意义：测试数据只写一处，多处复用——DRY 在测试里同样成立。

微任务卡（M2 · 讲解卡 · L2）：把 fixture 代码发给 AI："请解释 fixture 为什么能自动注入？不加 fixture 直接用全局变量有什么问题？"一句话记录理解。

就业红线（了解级边界）：fixture 只是测试的入门设施；测试开发岗位要求掌握参数化（parametrize，一组数据跑多个用例）、mock（模拟外部依赖，如不真发网络请求）、覆盖率统计（pytest-cov）。本课程先会用 fixture，就业后按这份清单进阶。

04. 17.3 测试驱动思维（TDD） ▼

17.3.1 概念认知：先写测试，再写代码

你之前是"先写代码、后手动验证"。测试驱动开发（TDD）反过来：先写测试（期望），再写代码让测试通过。

三步循环（红-绿-重构）：

红（RED）：写一个会失败的测试 → 运行，确认它失败（说明测试真的在测）
绿（GREEN）：写最小代码让测试通过
重构（REFACTOR）：改善代码结构，测试保持通过

17.3.2 语法掌握：一个 TDD 实例

代码案例 17.8：红——先写测试（❌ 此时会失败）

python
# test_avg.py
from calc import calc_average

def test_average():
    assert calc_average([90, 80, 70]) == 80.0

运行结果：

ERROR test_avg.py::test_average - ModuleNotFoundError: No module named 'calc'

（calc 里还没有 calc_average 函数——测试失败，符合"红"）

代码案例 17.9：绿——写最小实现让测试通过（✅ 正确）

python
# calc.py
def calc_average(scores):
    return sum(scores) / len(scores)

运行结果：

1 passed in 0.01s

讲解：先定义"应该怎样"，再实现"做到怎样"——测试就是你的"需求验收标准"（第 15 章的"可测试验收"在这里落地）。

就业提示：面试问"你写过单元测试吗"——不要只说"写过"，要说"我用 pytest 给 xx 函数写了边界用例，包含空列表、极值"，再加一个红-绿-重构的例子。测试是简历上性价比最高的技能点之一。

05. 17.4 综合案例：给成绩系统写测试 ▼

代码案例 17.10：calc_stats 被测函数（✅ 正确）

python
def calc_stats(scores):
    """返回 {total, avg, best, worst}；空列表返回 None"""
    if not scores:
        return None
    total = sum(scores)
    return {
        "total": total,
        "avg": total / len(scores),
        "best": max(scores),
        "worst": min(scores),
    }

代码案例 17.11：完整测试（✅ 正确）

python
from calc import calc_stats

def test_stats_normal():
    stats = calc_stats([88, 92, 76, 99, 61])
    assert stats["total"] == 416
    assert stats["best"] == 99
    assert stats["worst"] == 61

def test_stats_avg():
    stats = calc_stats([88, 92])
    assert stats["avg"] == pytest.approx(90.0)

def test_stats_empty():
    assert calc_stats([]) is None

def test_stats_single():
    stats = calc_stats([75])
    assert stats["avg"] == 75.0
    assert stats["best"] == 75

运行结果：

....                                                                     [100%]
4 passed in 0.01s

讲解：

  • 正常 + 边界全覆盖：5 个元素、2 个元素、空列表、单元素——每种情况一个测试函数；
  • test_stats_empty 专门守住"空列表返回 None"这个约定（防止以后有人改成除零崩溃）；
  • 这 4 个用例以后每次改 calc_stats 都自动跑——改代码的底气来自测试。

06. 17.5 本章 Debug 四件套 ▼

问题 1：测试文件找不到被测函数

问题代码：

python
from my_funcs import add      # my_funcs.py 不存在或不在同一目录

实际报错：

ModuleNotFoundError: No module named 'my_funcs'

提示：测试文件和被测文件要在同一目录；文件名拼对了吗？

讲解：pytest 从当前目录找模块。测试文件与被测文件放同一目录是初学者最省心的布局（项目大了再学 src 布局）。

问题 2：测试"全过"但代码有 bug

问题代码：

python
def test_average():
    assert calc_average([90, 80, 70]) == 80.0

实际表现：测试通过，但 calc_average([]) 会除零崩溃。

提示：测试覆盖了哪些情况？空列表测了吗？

讲解：测试通过 ≠ 代码没问题，只说明"你写过的用例都过"。漏掉边界用例，bug 就藏在那里。用例设计能力 = 测试的核心能力。

问题 3：浮点比较失败

问题代码：

python
assert calc_average([88, 92, 76]) == 85.33

实际输出：

assert 85.33333333333333 == 85.33

提示：85.33 能精确表示吗？回顾第 2 章 0.1+0.2 的教训。

讲解：浮点比较用 pytest.approx(85.33, abs=0.01) 或先 round。测试里直接 == 浮点数，是高频翻车点。

问题 4：测试之间互相影响

问题代码：

python
data = []

def test_add():
    data.append(1)
    assert len(data) == 1

def test_add_again():
    assert len(data) == 1     # 依赖上一个测试的状态

实际表现：第二个测试可能失败——因为 data 是全局的，测试顺序不保证。

提示：测试之间应该独立吗？共享状态应该放哪？

讲解：每个测试必须独立——不依赖其他测试、不依赖执行顺序。共享数据用 fixture（每个测试重新生成）。测试的顺序依赖是设计缺陷。

练习 1

第 7 题：给第 9 章"除法计算器"的 safe_divide(a, b) 写测试：正常（10/2=5.0）、小数（1/4=0.25）、除零（抛 ZeroDivisionError 或返回提示）、非数字（抛 ValueError）——先写测试再写实现。

📝 参考答案

先写测试（test_divide.py）：

python
import pytest
from calc import safe_divide

def test_normal():
    assert safe_divide(10, 2) == 5.0

def test_float():
    assert safe_divide(1, 4) == 0.25

def test_zero_division():
    with pytest.raises(ZeroDivisionError):
        safe_divide(1, 0)

def test_non_number():
    with pytest.raises(ValueError):
        safe_divide("a", 2)

再写实现（calc.py）：

python
def safe_divide(a, b):
    if not isinstance(a, (int, float)) or not isinstance(b, (int, float)):
        raise ValueError("参数必须是数字")
    return a / b
🔍 解析
  • pytest.raises(ZeroDivisionError) 断言"调用时抛出该异常"，不抛则测试失败；
  • 除法本身对除零会抛 ZeroDivisionError，所以实现不需要手动 raise；
  • 非数字参数先 isinstance 校验并 raise ValueError——测试驱动你写出了更健壮的实现。

08. 17.7 本章小结与知识树 ▼

知识树：

测试：让代码可验证
├── 为什么：手工验证不可靠 → 自动化回归保障
├── 测试金字塔：单元（多）→ 集成（中）→ 端到端（少）
├── pytest
│   ├── 安装：pip install pytest
│   ├── 约定：test_ 文件 / test_ 函数 / assert
│   ├── 运行：pytest -q；. 通过、F 失败、E 断言详情
│   ├── 边界用例：空列表 / 极值 / 非法输入 / 最小最大
│   ├── fixture：测试数据只写一处（自动注入）
│   └── 浮点比较：pytest.approx
├── TDD：红（先写失败测试）→ 绿（最小实现）→ 重构
├── 测试独立性：不依赖顺序、不共享全局状态
└── 核心认知：测试通过 ≠ 代码没问题；用例设计能力才是核心

必须记住的 5 件事：

  1. 测试文件 test_ 开头、函数 test_ 开头、用 assert；
  2. pytest -q：跑一遍全部用例，回归保障；
  3. 测试重点在边界：空列表、极值、非法输入；
  4. 浮点比较用 pytest.approx，不要直接 ==；
  5. 测试通过只说明"写过的用例都过"——用例设计能力才是核心。
