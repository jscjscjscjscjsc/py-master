02. Day 31｜MetaGPT：SOP 流水线式多角色协作 ▼

一、教学目标

  1. 说清 MetaGPT 的核心设计思路：把软件公司的 SOP 编码成 Agent 协作流程；
  2. 理解 Role / Action / Environment / Message 四个核心抽象的分工；
  3. 能对照第 6 章的三种协作模式，判断 MetaGPT 属于哪一类。

二、核心设计思路

MetaGPT 的出发点是一个观察：软件团队之所以能协作，是因为有 SOP（标准作业程序）—— 产品经理写 PRD，架构师据此设计，工程师实现，测试验证。每一步的输入输出格式是约定的。

所以 MetaGPT 做的事情是：

code
把「岗位职责 + 交付物格式」编码成 Agent 的 Role 和 Action
    ↓
用一个共享的消息池（Environment）让各角色按 SOP 顺序消费和产出
    ↓
于是「多智能体协作」变成了「消息驱动的流水线」

这个设计的关键洞察：多 Agent 协作的难点不是「让模型扮演角色」（那只是改 system prompt）， 而是「保证角色之间的接口稳定」——PRD 的结构必须让架构师能读懂，架构图必须让工程师能实现。 MetaGPT 用结构化的交付物 Schema 解决了这个问题。

对照第 6 章：MetaGPT 本质上是流水线模式（Day26 的模式一）， 但它比我们课堂上的版本严格得多——它给每个环节定义了强制的输出结构。

三、四个核心抽象

抽象职责对应你手写过的什么
Role一个岗位。持有 goal、约束、可执行的 Action 列表第 4 章的 Agent + system prompt
Action一个可执行的原子动作（写 PRD、画图、写代码）第 4 章的 Tool，但更重：它有自己的 prompt 模板和输出解析
Environment共享的消息空间与调度器第 6 章 Manager 的「任务分派」部分
Message结构化消息（带角色、内容、元数据）第 4 章的 messages 数组，但结构化程度高得多

Role 与 Action 的分离是设计要点：

python
# 简化示意（不是真实源码，用于说明结构）
class Role:
    goal: str                    # 这个岗位的目标
    actions: list[Action]        # 它能做哪些动作
    watch: set[MessageType]      # 它关心哪些消息

class Action:
    name: str
    prompt_template: str         # 这个动作的提示词（含 Few-shot 示例）
    output_schema: type          # 输出的结构（Pydantic 模型）
    async def run(self, context) -> Message: ...

为什么这样切分：

  • 一个 Role 可以有多个 Action（架构师既能设计模块，也能评审）；
  • 一个 Action 可以被多个 Role 复用（「写文档」这个动作产品经理和架构师都要做）；
  • output_schema 是接口契约——这是让流水线能自动串起来的关键。

03. Day 32｜Dify：可视化工作流与插件引擎 ▼

一、教学目标

  1. 理解「低代码编排」与「代码编排」各自的适用边界；
  2. 说清 Dify 工作流引擎的节点模型；
  3. 理解插件机制如何解决「工具生态」问题。

二、定位对比：Dify 与前面章节的关系

项目定位谁在用
MetaGPT用 SOP 生成软件工程交付物研究者、自动化内容生产
Dify可视化搭建 LLM 应用与工作流业务团队、非专业开发者、快速交付
LangGraph代码化的状态图编排工程团队、需要精细控制
你的迷你框架理解原理的教学工具你自己

Dify 的核心价值主张：把「编排」这件事从代码里搬到画布上。 不写代码也能搭出一个带知识库、工具调用、条件分支的应用。

三、工作流引擎的节点模型

Dify 的工作流是有向图，与 LangGraph 的 State/Node/Edge 是同构的——只是表达方式不同：

LangGraph（代码）Dify（画布）说明
State变量池 / 会话变量流转的数据
Node节点一个处理单元
Edge连线执行顺序
Conditional EdgeIf-Else 节点按条件路由
Checkpoint运行记录可回看每次执行的中间结果

为什么要在这里讲 Dify：让学生看到「同样的图结构，有两种表达方式」。 理解了这层同构关系，你就能：

  • 用 Dify 快速做原型验证，再决定是否值得用代码重写；
  • 看懂任何可视化编排工具（因为它们的概念几乎都是这一套）。

节点类型（已核实的官方枚举，核实日期 2026-09-21，Dify v1.17.1）：

类别节点名
流程控制Start Node / User Input / Answer / Output / If-Else / Iteration / Loop / Human Input / Variable Aggregator / Variable Assigner / List Operator
AI 能力LLM / Agent / Question Classifier / Parameter Extractor
数据Knowledge Retrieval / Document Extractor / Template / Code
集成Tool Node / HTTP Request
触发Trigger（下分 Schedule Trigger / Integration Trigger / Webhook Trigger）

教学提示：让学生对照这张表找「哪些是第 3 章的 RAG 环节」 （Knowledge Retrieval + Document Extractor）， 「哪些是第 2 章的后端能力」（HTTP Request）， 「哪些是第 5 章的图控制流」（If-Else / Iteration / Loop）。 同一个概念在不同工具里的名字不同，但本质相同——这是抽象能力的训练。

注意：Dify 官方文档没有公开工作流引擎的内部类名（如 WorkflowEngine 之类）。 如果你的报告里要写引擎的内部实现，需要自己读源码，不要凭猜测写。

四、插件机制

⚠️ 术语已变（核实日期 2026-09-21，Dify v1.17.1）： Dify 官方现在把扩展机制称为 Integrations（集成），不再叫 "plugins"。 搜索资料时用新词能查到更准的文档。

Dify 的集成体系解决的是生态问题：让第三方能给平台贡献能力，而不用改平台代码。

集成类型（官方枚举）：Model Provider、Tool、Data Source、Trigger、 Agent Strategy、Custom Endpoint、Extension。安装自 Marketplace。

开发者工具链：Dify Plugin CLI（PyPI 包 dify-plugin）、Manifest（YAML 清单）、 remote debugging（本地跑开发中的插件并挂到线上的 workspace）、插件 daemon 容器。

集成机制要解决的四个问题（这四个问题是通用的，不只是 Dify）：

问题解法
集成如何声明自己能做什么Manifest（YAML）+ 能力声明
权限边界如何界定声明所需权限，安装时由用户确认
版本兼容如何保证平台定义接口版本，集成声明兼容范围
恶意集成如何防范签名校验、权限最小化、沙箱执行

与 MCP 的关系：Dify 的 Integration 是平台内的能力扩展机制， MCP 是跨平台的工具协议。两者解决的问题层次不同，也常一起用 （Dify 可以作为 MCP Client 去调用 MCP Server）。 不要把它们当成竞争关系 —— 这是面试时容易被问到的一个辨析点。

04. Day 33｜OpenHands 与 deer-flow：执行循环与长任务管理 ▼

一、教学目标

  1. 理解「Agent 真的去执行代码」需要额外解决哪些工程问题；
  2. 说清沙箱隔离的必要性与实现层次；
  3. 理解长任务管理器的设计要点。

二、从「调用工具」到「执行代码」的跳跃

第 4 章的工具调用是这样的：模型输出 {"name": "get_weather", "arguments": {...}}， 你的程序校验参数、执行函数、返回结果。风险是可控的——因为可执行的函数是你预先注册的。

Code Agent 是另一回事：模型生成一段代码，你去执行它。

维度工具调用（第 4 章）代码执行（Code Agent）
可执行范围预注册的函数（白名单）任意代码
风险参数错误、越权调用任意代码执行、文件读写、网络访问、资源耗尽
参数校验Pydantic 严格校验无法穷举，只能靠沙箱
出错恢复返回结构化错误可能把环境搞坏（删文件、装错包）

所以 Code Agent 的核心工程问题是沙箱，不是提示词。

三、沙箱的层次

层次手段隔离强度代价
1限制可导入模块（import 白名单）弱低（容易被绕过）
2子进程 + 超时 + 资源限制中中
3容器（Docker）+ 无网络 + 只读挂载较强中高
4虚拟机 / 微虚拟机强高
5独立机器 / 云沙箱服务最强最高

必须记住的一条：任何依赖「在同一个进程里跑 Python 并拦截危险操作」的方案都不是安全边界。 Python 的动态特性决定了这类拦截可以被绕过。真正的边界必须是操作系统级或进程级的。

沙箱除了安全，还要解决：

  1. 状态隔离：多次执行之间是否共享文件系统？不隔离会互相污染；
  2. 依赖管理：模型装的包会不会破坏宿主环境？
  3. 超时与资源：一个死循环会占满 CPU；
  4. 可复现：同样的任务两次执行，环境是否一致。

四、长任务管理器

一个跑几分钟到几十分钟的任务，需要额外的机制：

机制作用
持久化会话进程重启后任务能继续
状态快照中途失败能从最近的检查点恢复，而不是从头再来
进度可见用户能看到「现在在第几步、在做什么」
中断与取消用户能叫停
产出归档长任务的中间产物要落盘（否则进程没了就全丢了）
并发控制多个长任务同时跑时，资源如何分配

对照你自己的实现：第 6 章 Day29 的 61_long_task.py 其实就是一个极简的长任务管理器。 你实现了任务拆解、进度查询、上下文压缩。OpenHands 在生产环境要处理的是同样的问题， 只是多了沙箱隔离、崩溃恢复、并发调度、资源配额。 这就是「从课堂到生产」的差距所在——不是算法更难，而是边界情况多得超出想象。

五、精读建议

⚠️ 项目已重构拆仓（核实日期 2026-09-21）——这是本章最需要注意的状态变化：

OpenHands 不再是单一仓库，架构已整体改变：

组件仓库当前版本职责（官方原文）
Agent CanvasOpenHands/OpenHandsv1.20.0"the open-source browser client and control center for agent conversations and automations"
Software Agent SDKOpenHands/software-agent-sdkv1.49.2"a composable Python library for building agents that work with code"
Agent Server同上—"exposes agent execution, conversations, tools, and workspaces through REST and WebSocket APIs"
Sandbox Server同上—"creates and manages sandboxed environments that host Agent Server"
Automation Server同上—定时与事件驱动的自动化生命周期
CLI同上—终端界面，基于 Software Agent SDK

旧架构已归档到 OpenHands/legacy：之前教程里常提到的 Docker Runtime、Action Execution Server、ActionExecutor、EventStream、 docker_runtime.py / local_runtime.py 等都属旧架构，现在在 legacy 仓库里。 网上大量中文教程仍在讲旧架构 —— 读之前先确认讲的是哪一代。

文档域名也从 docs.all-hands.dev 迁到 docs.openhands.dev。

新架构的核心设计原则（官方原文）：

  • Agent "Implements the reasoning-action loop"（实现推理-行动循环）；

这是本课程最有成就感的一天。 你要把前面 33 天学到的一切， 抽象成一个自己能讲清楚每一行的框架。

一、教学目标

  1. 综合运用前 33 天的知识，自研一个百行级 Agent 框架；
  2. 用分层设计解决「可替换」与「可测试」两个工程问题；
  3. 写出一份能作为作品集的架构文档。

二、框架的分层设计

flowchart TD
    A[用户代码] --> B[Runner 执行器]
    B --> C[Agent 智能体]
    C --> D[LLM 抽象]
    C --> E[Tool 系统]
    C --> F[Memory 记忆]
    D --> G[OpenAICompatibleLLM]
    G --> H[LLMClient<br/>第1章交付物]
    E --> I[ToolRegistry]
    E --> J["@tool 装饰器"]
    F --> K[BufferMemory]
    F --> L[SummaryMemory]
    C --> M[Message 消息抽象]

每一层解决一个问题：

层解决什么问题为什么必须独立成层
LLM屏蔽不同平台的差异换模型不改业务代码；测试可以用假模型
Tool + Registry工具的注册、Schema 生成、调用、校验加工具不改 Agent 逻辑
Memory上下文的管理策略换策略（缓冲/摘要）不改 Agent 循环
Message消息的结构化表示保证与 OpenAI 格式的转换只有一处实现
Agent决策逻辑（调不调工具、何时结束）换决策范式（单次/ReAct）不动其他层
Runner循环控制、步数限制、步骤记录执行策略（如加重试、加追踪）集中在一处

这个分层不是抄来的，是从你在第 4 章踩过的坑里长出来的：

第 4 章的坑抽象出什么层
tool 消息 content 传了 dict 导致 400Message 层统一处理格式转换
llm.decide() 到处手写解析逻辑LLM 层归一化响应
参数校验散落在各处Tool 层用 Pydantic 统一校验
加一个新的记忆策略就要改 Agent 循环Memory 层定义接口
步数、超时、追踪逻辑和决策逻辑混在一起Runner 层独立

这就是「封装」的正确理解方式：不是为了「看起来专业」而分层， 而是每一层都对应一个你真实遇到过的变化点。

三、关键实现要点

@tool 装饰器：从函数签名自动生成 Schema

python
@tool
def calculator(expression: str, precision: int = 2) -> str:
    """计算一个数学表达式。

    Args:
        expression: 要计算的表达式，如 "1+2*3"
        precision: 结果保留的小数位数
    """
    ...

装饰器要做四件事：

  1. 读类型标注 → 生成 JSON Schema 的 type；
  2. 读 docstring 的 Args 段 → 生成每个参数的 description（这个描述直接影响模型能否正确调用工具）；
  3. 读默认值 → 决定哪些参数是必需的；
  4. 保留原函数 → 调用时直接执行。

教学要点：为什么用装饰器而不是让用户手写 JSON Schema？ 因为手写 Schema 有双重维护问题——改了函数签名忘了改 Schema， 就会得到「模型按 Schema 传参，但函数不认」的诡异 bug。 装饰器让签名成为唯一事实源。

Memory 抽象：策略模式

python
class Memory(ABC):
    @abstractmethod
    def add(self, message: Message) -> None: ...

    @abstractmethod
    def get_context(self) -> list[Message]: ...

两个实现：

实现策略代价
BufferMemory保留最近 N 条简单，但会丢失早期信息
SummaryMemory早期内容摘要成一条省 token，但有损，且摘要本身要花钱

呼应第 6 章：这就是「上下文治理」的框架级抽象。

Runner：把控制流集中

Runner 负责「循环怎么转、什么时候停、每一步记什么」。它的职责边界如下 （骨架示意，完整实现见 code/ch07/miniagent/runner.py）：

python
class Runner:
    """执行器：驱动 Agent 循环，控制终止条件，记录每一步。

    为什么把它从 Agent 里分出来：
      Agent 只回答「下一步做什么」，Runner 回答「循环怎么转」。
      加追踪、加预算护栏、加人工确认 —— 全都是改 Runner 一处。
    """

    def run(self, agent, task, max_steps: int = 10, timeout: float = 60) -> RunResult:
        # 循环体：agent.step() → 检查终止条件 → 记录步骤
        # 四个终止条件：任务完成 / 达到步数 / 超时 / 出错
        ...

把它独立出来的价值：想加追踪（第 6 章）？改 Runner 一处。 想加预算护栏？改 Runner 一处。想加中途人工确认？还是改 Runner 一处。

抽象自检问题：如果你发现「加一个新功能需要改三个文件」， 说明分层划错了 —— 变化点没有被隔离在单层里。 这是判断抽象是否合理的最实用标准，比任何设计原则都直接。
