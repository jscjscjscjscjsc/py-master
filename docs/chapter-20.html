02. 20.1 协作工作流 ▼

20.1.1 概念认知：从单人提交到团队协作

单人工作流（你现在的习惯）：main 上直接开发 → 测试 → 提交 → 推送。

小组工作流：main 是"稳定主干"，所有人不在 main 上直接改，而是：

1. 从 main 拉一个 feature 分支：git checkout -b feature-xxx
2. 在分支上开发 + 提交
3. 推送到远程：git push -u origin feature-xxx
4. 发起 Pull Request
5. 队友评审 → 修改 → 通过
6. 合并进 main

为什么这么麻烦：

  • main 永远是"能跑的版本"——线上出问题随时可以回滚到 main；
  • 每个改动都经过评审——错误在上线前被拦下；
  • 提交历史清晰——每个 PR 就是一个"功能单元"。

原理探秘：四眼原则（Four-Eyes Principle）

重要操作必须至少两个人看过才能执行——这是金融、工程、软件行业的通用纪律。PR + 评审就是把"四眼原则"落在代码上：作者负责"想"（实现），评审者负责"看"（把关），两人都同意才合入。单人疏忽会被第二双眼睛拦下——这就是流程看起来"麻烦"却值得的原因。

20.1.2 语法掌握：提交信息规范（Conventional Commits）

提交信息决定"历史可读性"。规范格式：

<类型>: <一句话描述>

代码案例 20.1：类型速查（✅ 正确）

feat: 添加成绩统计功能          # 新功能
fix: 修复除零崩溃                # 修 bug
docs: 更新 README               # 文档
test: 补充 is_prime 边界用例     # 测试
refactor: 拆分 calc_stats 函数   # 重构（不改变功能）
style: 统一命名规范              # 格式/命名

交叉验证：坏提交信息 vs 好提交信息

❌ 坏：更新、修改代码、fix bug、111

✅ 好：fix: 修复空列表时平均分除零崩溃

讲解：好信息回答"这次改动做了什么、为什么"——半年后看 log 也能秒懂。"类型: 描述"是行业标准，企业评审会检查提交信息。

20.1.3 语法掌握：分支命名规范

feature/成绩统计        # 新功能
fix/修复登录超时         # 修 bug
docs/更新README         # 文档

讲解：分支名 = "类型/一句话"。PR 里看到分支名就知道改的是什么，评审更有针对性。

03. 20.2 Code Review：让代码"过堂" ▼

20.2.1 概念认知：为什么要评审

Code Review（代码评审）= 合并前让队友看你的改动。它保护双方：

  • 对作者：多一双眼睛，少一个上线事故；
  • 对团队：知识共享（别人也会看你的代码风格）；
  • 对评审者：读别人代码是最快的进阶学习。

心态：评审是"一起把代码变好"，不是"找茬"。被提意见 ≠ 你不行——所有资深工程师都在被 review。

20.2.2 语法掌握：Review 清单

评审时按清单逐项检查（合并进你以后的工作习惯）：

检查项问什么
功能实现符合需求吗？边界情况（空/极值）处理了吗？
命名变量/函数名见名知意吗？符合 PEP 8 吗？
逻辑有没有潜在 bug（类型错误、优先级、除零）？
测试有新功能对应的测试吗？测试覆盖边界了吗？
性能有没有明显低效（循环里拼字符串、重复计算）？
安全输入校验了吗？有密钥硬编码吗？

20.2.3 语法掌握：评审实战（案例 20.2）

待评审代码（❌ 埋了 3 个问题）：

python
def get_avg(scores):
    total = 0
    n = len(scores)
    for s in scores:
        total = total + s
    return total / n

def check(score, limit=60):
    if score >= limit:
        return "pass"
    else:
        return "fail"

评审意见（✅ 示例）：

1. 【边界】get_avg([]) 会除零崩溃——空列表应返回 0 或抛异常并说明；
2. 【逻辑】check 的 else 是多余的，卫语句风格可读性更好；
3. 【规范】"pass" 是 Python 关键字（虽然作为字符串没问题），建议改名 "passed" 避免歧义。

交叉验证：你能找出第 4 个问题吗？

提示：total = total + s 没问题，那问题在"性能"还是"命名"还是"类型"？

讲解：scores 如果来自用户输入（字符串列表），total + s 会 TypeError——评审时假设"输入不可信"，要问"调用方传的是什么类型"。这就是"边界 + 类型"的评审思维。

微任务卡（M1 · 审查卡 · L3）：把案例 20.2 的代码发给 AI："请按 Review 清单（功能/命名/逻辑/测试/安全）评审这段代码。"对照你自己的发现，记录 AI 提出而你没发现的 1-2 个问题。

04. 20.3 AI 辅助 Code Review（L3） ▼

20.3.1 语法掌握：AI 评审的正确姿势

AI 很擅长"按清单找问题"，但它可能误报、漏报、或给出与项目上下文不符的建议。所以：

AI 评审的正确用法：
1. 给它清单（功能/命名/逻辑/测试/安全）+ 被评审的 diff 或代码；
2. 让它"逐条列出问题 + 理由 + 严重程度"；
3. 你逐条复核：能复现的采纳，不认同的否决并说明；
4. 把结论写进 PR 评论（谁提的问题、怎么处理的）。

参考提问句式：

请按以下清单评审这段 Python 代码：
1. 功能与边界（空输入、极值、非法输入）；
2. 命名与 PEP 8；
3. 潜在 bug（类型、优先级、除零）；
4. 测试覆盖建议；
5. 安全（输入校验、硬编码密钥）。
每条问题请给出：位置、理由、严重程度（高/中/低）。不要修改代码。

20.3.2 交叉验证：AI 评审的三个坑

❌ 坑 1：AI 建议"改成一行推导式"——但代码可读性反而下降（第 12 章"推导式可读性灾难"）； ❌ 坑 2：AI 说"这里可能有问题"，实际是它的误判——不复现不采纳； ❌ 坑 3：让 AI"直接给出修改后的完整代码"然后无脑合入——评审变成了代写，失去意义（L3 规则：生成必须 Review，评审本身更要人工把关）。

判别标准：AI 是"第二双眼睛"，你才是"最终决定者"——所有建议以"你能解释为什么"为采纳前提。

05. 20.4 综合工作坊：小组 PR 互审 ▼

目标：完整走一遍"feature 分支 + PR + 评审 + 合并"。

准备：2-3 人一组，组长在 Gitee 建仓库并开启 main 分支保护（设置 → 分支设置 → 禁止直接推送）。

步骤：

  1. 每人从 main 拉分支 feature/自己的功能，开发一个小功能（如"添加任务"），本地测试通过；
  2. git push -u origin feature/xxx；
  3. 在 Gitee 发起 Pull Request（描述：改了什么、怎么测的）；
  4. 队友按 Review 清单评论（每条：位置 + 理由 + 严重程度），作者回复并修改；
  5. 全部问题处理后，评审通过 → 合并；
  6. 全体 git pull 到最新 main；
  7. 复盘：每人写"我收到的评审意见里，最有价值的一条是什么？为什么？"

微任务卡（M2 · 审查卡 · L3）：把队友的 PR diff 发给 AI 预审，再结合自己的 Review 清单出最终意见——记录"AI 找到的、我没发现的"和"我发现的、AI 漏掉的"各一条。

06. 20.5 本章 Debug 四件套 ▼

问题 1：直接在 main 上开发

问题描述：小组里有人图省事，直接在 main 上改代码推上去（分支保护拦截后仍继续）。

后果：main 被改坏，全组拉下来都是坏代码；评审形同虚设。

讲解：main 是"稳定主干"，一切开发走 feature 分支 + PR。这不是效率低，是保护全组。

问题 2：PR 描述空白

问题描述：PR 只有代码没有说明，评审者看不懂改了什么。

后果：评审效率低，甚至没人敢合。

讲解：PR 描述 = 变更说明：改了什么功能、为什么改、怎么测试的、有没有破坏性变更——按需求文档的"验收标准"思路写。

问题 3：评审意见没有"理由"

问题描述：评论只写"这里不对""这里改一下"，作者不知道改什么、为什么。

后果：来回拉扯，作者不信任评审。

讲解：每条意见 = 位置 + 理由 + 严重程度（参考 20.2.3 的示例）。有理由的意见才叫评审，没理由的叫抱怨。

问题 4：AI 意见无脑全收

问题描述：AI 提了 10 条意见，作者全改，结果把原本好的代码改乱了。

后果：引入了新 bug，评审变成了"听 AI 的"。

讲解：AI 意见必须逐条复核（能复现才采纳），并在 PR 里写"采纳 X / 否决 Y（理由）"——这是 L3 的核心纪律。

08. 20.7 本章小结与知识树 ▼

知识树：

团队协作工作流与 Code Review
├── 工作流
│   ├── 单人：main 直接开发（个人项目）
│   └── 小组：feature 分支 → push → PR → 评审 → 合并（main 稳定主干）
├── 规范
│   ├── 提交信息：feat:/fix:/docs:/test:/refactor:/style:
│   └── 分支命名：feature/xxx、fix/xxx、docs/xxx
├── Code Review
│   ├── 清单：功能边界 / 命名 / 逻辑 / 测试 / 性能 / 安全
│   ├── 意见格式：位置 + 理由 + 严重程度
│   └── 心态：一起变好，不是找茬
├── AI 辅助评审（L3）
│   ├── 给清单 + 代码 → 逐条意见 → 人工复核
│   └── 三个坑：误报 / 漏报 / 无脑代写
└── 终极纪律：AI 是第二双眼睛，你才是最终决定者

必须记住的 5 件事：

  1. main 是稳定主干，一切改动走 feature 分支 + PR；
  2. 提交信息格式：类型: 描述（feat/fix/docs/test/refactor）；
  3. Review 意见格式：位置 + 理由 + 严重程度；
  4. Review 清单：功能边界 / 命名 / 逻辑 / 测试 / 性能 / 安全；
  5. AI 评审意见必须逐条人工复核——采纳要能解释，否决要有理由。

markdown
# 团队协作约定

## 1. 分支规范
- main：稳定主干，禁止直接推送（开启分支保护）；
- 新功能：feature/功能名；修 bug：fix/问题描述。

## 2. 提交规范
- 格式：`类型: 描述`（feat / fix / docs / test / refactor / style）；
- 一次提交只做一件事。

## 3. Code Review 清单
功能边界 / 命名 / 逻辑 / 测试 / 性能 / 安全；
意见格式：位置 + 理由 + 严重程度。

## 4. PR 描述模板
- 改了什么；
- 为什么改；
- 怎么测试的；
- 是否有破坏性变更。
🔍 解析

这份文档提交到 docs/ 后，就是小组的"团队宪法"——新人看它就能上手协作。
