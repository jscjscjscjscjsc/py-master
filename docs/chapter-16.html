02. 16.1 设计原则 ▼

16.1.1 概念认知：设计是什么

设计（design） 是编码之前的"布局"：模块怎么分、函数怎么拆、数据怎么流。设计得好，改需求时只动一小块；设计得差，改一个功能牵一发动全身。

16.1.2 语法掌握：单一职责原则（SRP）

一个函数/类只做一件事——这是最重要、最容易理解的设计原则。

代码案例 16.1：职责过多 vs 单一职责（❌ vs ✅）

python
# ❌ 一个函数干三件事：输入、统计、打印
def process_scores():
    scores = []
    while True:
        s = input("成绩（回车结束）：")
        if s == "":
            break
        scores.append(int(s))
    total = sum(scores)
    avg = total / len(scores)
    print(f"总分 {total}，平均 {avg:.1f}")

# ✅ 三个函数各干一件事，可以单独测试、单独复用
def input_scores():
    """收集成绩，返回列表"""
    ...

def calc_stats(scores):
    """统计，返回字典"""
    ...

def print_report(stats):
    """打印报告"""
    ...

交叉验证：为什么"顺便打印"是坏味道？

❌ 问题：统计函数里顺便打印，测试时没法只验证"统计结果"（输出混在结果里）；以后想改成写文件、发消息，得改统计函数。

✅ 解法：函数只 return 结果，输出交给调用者决定——这就是你 Day 7 学过的"函数 = 接口"。

16.1.3 语法掌握：高内聚、低耦合

  • 高内聚：一个模块里的东西关系紧密（学生相关都在一起）；
  • 低耦合：模块之间依赖少、接口清晰（改 A 不影响 B）。

代码案例 16.2：耦合对比（❌ vs ✅）

python
# ❌ 高耦合：主程序直接读写文件、算统计、打印，全搅在一起
# （改文件格式要动主程序，改统计也要动主程序）

# ✅ 低耦合：三个模块各自独立，通过"返回值/参数"协作
# file_utils.read_scores(path) → 列表
# score_utils.calc_stats(scores) → 字典
# main.py 只负责"调用谁、传什么、展示什么"

讲解：低耦合的检验方法——"改需求 A，会不会被迫改模块 B？" 数据层改格式，统计层和展示层应该毫不知情。

16.1.4 语法掌握：DRY——不要重复自己

代码案例 16.3：重复代码 vs 提取函数（❌ vs ✅）

python
# ❌ 相同的校验逻辑写三遍
age = int(input("年龄："))
if age < 0 or age > 150:
    print("年龄不合法")
score = int(input("成绩："))
if score < 0 or score > 100:
    print("成绩不合法")
...

# ✅ 提取成一个校验函数
def check_range(value, low, high, name):
    if value < low or value > high:
        print(f"{name}不合法")
        return False
    return True

讲解：复制三遍 = bug 改三处、漏一处就出事故。DRY 不是"代码越少越好"，而是"每一份知识只保留一个权威来源"。

16.1.5 语法掌握：分层思想

代码案例 16.4：未分层 vs 分层（❌ vs ✅）

python
# ❌ 三层混在一起：界面逻辑 + 业务逻辑 + 数据逻辑 全在 main
def main():
    # 界面：print 菜单、input 选择
    # 业务：算平均、判断及格
    # 数据：open json 读写
    ...

# ✅ 分三层（你 Day 9 的成绩系统 v3 已经是雏形）
# 表现层：菜单、输入输出（main.py）
# 逻辑层：统计、判断（score_utils.py）
# 数据层：读文件、写文件（file_utils.py）

讲解：分层 = 同层之间不互相掺和。改界面不影响逻辑，换数据库不影响统计——这就是第 21 章软件架构的起点。

16.1.6 了解：SOLID 一句话版

SOLID 是面向对象设计的五个原则缩写，本课程要求记住"一句话含义"：

字母原则一句话
S单一职责一个类只做一件事
O开闭原则对扩展开放、对修改关闭（加功能不改老代码）
L里氏替换子类应该能替换父类而不出错（第 11 章继承的"体检"）
I接口隔离不要强迫使用者依赖用不到的接口
D依赖倒置依赖抽象，不依赖具体实现

就业提示：面试问"你了解设计原则吗"，答"S 单一职责 + O 开闭"加一个例子，就够过初面；能说出全部五个是加分项。

03. 16.2 代码质量：让代码"可读" ▼

16.2.1 语法掌握：命名规范（PEP 8）

代码案例 16.5：坏命名 vs 好命名（❌ vs ✅）

python
# ❌
def f(a, b):
    x = a * b
    return x

# ✅
def calc_rectangle_area(width, height):
    area = width * height
    return area

PEP 8 命名四规则（复习 + 强化）：

  1. 变量/函数：小写 + 下划线（total_score）；
  2. 类名：大驼峰（BankAccount）；
  3. 常量：全大写（MAX_RETRY = 3）；
  4. 函数名要"动词 + 名词"（calc_stats、save_report）。

16.2.2 语法掌握：注释与文档字符串

代码案例 16.6：注释的三种用途（✅ 正确）

python
def calc_stats(scores):
    """计算成绩统计，返回 (总分, 平均分)。"""
    # 空列表直接返回，避免除零
    if not scores:
        return 0, 0
    total = sum(scores)
    return total, total / len(scores)

讲解：

  • 文档字符串 """..."""：解释函数"是什么"（供调用者读，PyCharm 悬停可见）；
  • 行注释 #：解释"为什么这么写"（供维护者读，重点写"不明显的意图"）；
  • 不要写废话注释：x = x + 1 # 让 x 加 1——注释要和代码互补，不是复述。

16.2.3 了解：类型提示

代码案例 16.7：类型提示（✅ 正确，了解级）

python
def calc_stats(scores: list[int]) -> tuple[int, float]:
    """scores: 成绩列表；返回 (总分, 平均分)"""
    total = sum(scores)
    return total, total / len(scores)

讲解：scores: list[int] 声明"期望传入整数列表"，-> tuple[int, float] 声明"返回元组"。它不强制检查（还是动态类型），但让读者和 IDE 一眼看懂接口——大型项目标配，本课程了解即可，第 30 章项目里用到再看。

原理探秘：可读性的经济学

代码被阅读的次数远多于编写的次数（行业流传"读:写 ≈ 10:1"）：你现在写的每一行，将来会被自己、队友、接手的人反复读。命名、注释、结构不是"洁癖"，而是经济决策——可读性差的代码，维护成本由整个团队买单。这也是企业代码评审第一条看命名的原因。

就业红线（了解级边界）：类型提示这里只要求"认识"；后端岗位（尤其 FastAPI/Django 项目）会要求实际使用——FastAPI 的参数与响应模型全靠类型标注。面试可答："类型提示是轻量静态检查，FastAPI 用它生成接口文档与校验。"

04. 16.3 重构：不改变功能，改善结构 ▼

16.3.1 概念认知：重构是什么

重构（refactoring） = 在不改变程序外部行为的前提下，改善内部结构。前提是先有测试（第 17 章）——没有测试的重构像走钢丝。

16.3.2 语法掌握：识别坏味道

四个最常见的"坏味道"：

坏味道症状药方
魔法数字代码里到处是 86400、0.6提取为常量
长函数一个函数 50 行提取函数
重复代码相同逻辑复制粘贴提取函数（DRY）
命名差a、x1、data2见名知意

16.3.3 语法掌握：三个基础手法（重构前后对比）

代码案例 16.8 · 手法一：消除魔法数字（❌ → ✅）

python
# ❌ 魔法数字
if retry_count >= 3:
    raise ConnectionError("重试次数过多")

# ✅ 常量
MAX_RETRY = 3
if retry_count >= MAX_RETRY:
    raise ConnectionError(f"超过最大重试次数 {MAX_RETRY}")

代码案例 16.9 · 手法二：提取函数（❌ → ✅）

python
# ❌ 主流程里塞了判断逻辑
for row in rows:
    if row[1].isdigit() and 0 <= int(row[1]) <= 100:
        clean.append(row)

# ✅ 提取为"表达意图"的函数
def is_valid_score(text):
    return text.isdigit() and 0 <= int(text) <= 100

for row in rows:
    if is_valid_score(row[1]):
        clean.append(row)

代码案例 16.10 · 手法三：简化条件（❌ → ✅）

python
# ❌ 多层嵌套，读起来像迷宫
if user:
    if user.get("logged_in"):
        if user.get("role") == "admin":
            return "允许访问"
    return "拒绝"

# ✅ 卫语句提前返回（Day 7 学过）
if not user:
    return "拒绝"
if not user.get("logged_in"):
    return "拒绝"
if user.get("role") != "admin":
    return "拒绝"
return "允许访问"

16.3.4 手法速览：六组高频对比

代码案例 16.11 · 手法四：引入解释性变量（❌ → ✅）

python

代码案例 16.12 · 手法五：用数据表替代 if-elif 链（❌ → ✅）

python
# ❌ 五层 elif 的等级判断
if score >= 90:
    grade = "优秀"
elif score >= 80:
    grade = "良好"
...

# ✅ 边界列表 + 循环（规则集中、易扩展）
levels = [(90, "优秀"), (80, "良好"), (70, "中等"), (60, "及格")]
grade = "不及格"
for bound, label in levels:
    if score >= bound:
        grade = label
        break

python

    if False:               # 永远不执行

代码案例 16.15 · 手法八：合并重复分支（❌ → ✅）

python
# ❌ 两个分支做同一件事

    price = price * 0.8

代码案例 16.16 · 手法九：拆分长函数（❌ → ✅）

python
# ❌ 30 行的"做一切"函数
def process_order(order):
    # 校验订单（10 行）
    # 计算金额（10 行）
    # 更新库存（10 行）
    ...

# ✅ 三个小函数 + 主流程三行调用
def validate_order(order): ...
def calc_amount(order): ...
def update_stock(order): ...
def process_order(order):
    validate_order(order)
    amount = calc_amount(order)
    update_stock(order)
    return amount

讲解：基础三手法 + 速览六手法，覆盖了 80% 的日常重构场景。练习方法：每次写完代码，用这 9 个手法挨个问一遍"有没有可以套用的"——重构能力就是这样练出来的。

16.3.5 综合运用：重构实战

代码案例 16.17：重构前（❌ 能跑但结构差）

python
def main():
    d = {}
    while True:
        print("1加 2查 3删 4退")
        c = input()
        if c == "1":
            n = input("名")
            s = int(input("分"))
            d[n] = s
        elif c == "2":
            n = input("名")
            if n in d:
                print(d[n])
            else:
                print("无")
        elif c == "3":
            n = input("名")
            d.pop(n, None)
        elif c == "4":
            break

代码案例 16.18：重构后（✅ 结构清晰）

python
STUDENTS = "students.json"

def load_data() -> dict:
    """从文件加载成绩表"""
    ...

def save_data(data: dict) -> None:
    """保存成绩表到文件"""
    ...

def add_student(data: dict) -> None:
    """添加学生成绩"""
    ...

def query_student(data: dict) -> None:
    """查询学生成绩"""
    ...

def delete_student(data: dict) -> None:
    """删除学生成绩"""
    ...

def main():
    data = load_data()
    while True:
        choice = show_menu()
        if choice == "1":
            add_student(data)
        elif choice == "2":
            query_student(data)
        elif choice == "3":
            delete_student(data)

讲解：

  • 每个函数 3-5 行，名字就是意图；
  • 魔法数字换成常量、单字母变量换成全名；
  • 主流程变成"菜单 + 调用"——读主函数 10 秒就知道程序在干什么；
  • 行为没变，结构大变——这就是重构。

if age > 150:

问题 2：函数职责过多

问题代码：

python
def handle(name):
    data = load()
    data[name] = input("分数：")
    save(data)
    print("成功")

问题：这个函数干了四件事，哪件属于"数据层"？哪件属于"表现层"？

讲解：输入、加载、保存、打印混在一起——测试 handle 必须模拟输入和文件。拆成 add_student（逻辑）+ 数据函数 + 界面函数。

问题 3：注释复述代码

问题代码：

python
total = total + score   # 把 score 加到 total 上
count += 1              # count 加 1

问题：这两条注释提供了什么新信息？

讲解：没有——它们在复述代码。注释写"为什么"，不写"是什么"（如 # 跳过空行，避免 int() 报错）。

问题 4：复制粘贴的重复逻辑

问题代码：

python
if 0 <= int(a) <= 100 and str(a).isdigit():
    ...
if 0 <= int(b) <= 100 and str(b).isdigit():
    ...

问题：如果规则变成"0-120"，要改几处？漏改会发生什么？

讲解：两处校验逻辑不一致时（一处 isdigit 顺序错了），同一个 bug 只在一个地方出现——这就是重复代码的可怕之处。提取 is_valid_score 函数。

07. 16.6 本章小结与知识树 ▼

知识树：

设计思维与代码质量
├── 设计原则
│   ├── 单一职责：一个函数/类只做一件事
│   ├── 高内聚低耦合：模块内紧密、模块间依赖少
│   ├── DRY：一份知识只保留一个权威来源
│   ├── 分层：表现层 / 逻辑层 / 数据层
│   └── SOLID 一句话版（了解）
├── 代码质量
│   ├── PEP 8：小写下划线 / 大驼峰 / 全大写常量 / 动词+名词
│   ├── 注释：写"为什么"不写"是什么"；文档字符串
│   └── 类型提示（了解）
└── 重构（不改变功能、改善结构）
    ├── 坏味道：魔法数字 / 长函数 / 重复代码 / 命名差
    ├── 手法：提取常量 / 提取函数 / 卫语句简化条件
    └── 前提：先有测试（第 17 章）

必须记住的 5 件事：

  1. 单一职责是最重要也最容易做的设计原则；
  2. 高内聚低耦合的检验法："改需求 A 会不会被迫动模块 B？"；
  3. DRY = 一份知识一个权威来源，不是"代码越少越好"；
  4. 重构的铁律：先有测试，再重构；不改变功能，只改善结构；
  5. 注释写"为什么"，命名写"是什么"。
