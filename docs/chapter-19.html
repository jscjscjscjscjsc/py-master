02. 19.1 远程仓库概念 ▼

19.1.1 概念认知：本地 vs 远程

到目前为止你的仓库都在自己电脑上（本地）。远程仓库（remote） 是托管在服务器上的副本（Gitee 的服务器），作用：

  1. 备份：电脑坏了，代码不丢；
  2. 协作：队友从同一仓库 clone/push/pull；
  3. 作品集：面试官看的"代码门面"。
你的电脑（本地）          Gitee 服务器（远程）
  master ◄──push──────── master
  master ──pull/clone──► master

19.1.2 概念认知：SSH vs HTTPS

连接远程仓库有两种方式：

方式原理优点缺点
HTTPS每次推送要用户名 + 密码/令牌配置简单反复输密码（可缓存）
SSH密钥对（公钥放 Gitee，私钥在自己电脑）免密推送、更安全首次配置稍麻烦

本课程建议 SSH（配置一次，之后免密；企业里 SSH 是主流）。配置步骤：ssh-keygen 生成密钥 → 把公钥粘贴到 Gitee"设置 → SSH 公钥"。

原理探秘：SSH 为什么能免密

SSH 用一对密钥工作：公钥（可以公开，粘贴到 Gitee"SSH 公钥"设置）与私钥（必须保密，只存在自己电脑）。推送时，Gitee 服务器用你的公钥验证"你确实持有对应的私钥"——验证通过即放行，全程不用输密码。私钥 = 你的"数字身份证"，泄露私钥等于把仓库交出去。

03. 19.2 Gitee 建仓与推送 ▼

19.2.1 语法掌握：创建仓库

  1. 登录 <https://gitee.com>，右上角"+"→ 新建仓库；
  2. 填仓库名（如 python_work）、选择公开/私有；
  3. 勾选"初始化仓库"（生成 README 和 .gitignore）——或者不勾选，用命令行推已有仓库；
  4. 创建后页面会显示两种推送命令（HTTPS/SSH 各一套）。

19.2.2 语法掌握：把本地仓库推上去

代码案例 19.1：关联远程并推送（✅ 正确）

powershell
git remote add origin git@gitee.com:你的用户名/python_work.git
git branch -M main
git push -u origin main

运行结果（首次推送）：

Enumerating objects: 25, done.
...
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

讲解：

  • git remote add origin 地址：给远程仓库起名叫 origin（惯例名字）；
  • git branch -M main：把默认分支改名为 main（现代惯例，原 master 也可）；
  • git push -u origin main：推送并设置"跟踪"（-u 之后直接 git push 即可）；
  • 首次推送可能要求输入 SSH 密码/确认指纹，正常现象。

微任务卡（M1 · 讲解卡 · L3）：把 remote add / push 的输出发给 AI："请解释 -u 参数的作用、origin 和 main 分别指什么。"一句话记录理解。

19.2.3 语法掌握：clone 与 pull

代码案例 19.2：克隆别人的仓库（✅ 正确）

powershell
git clone git@gitee.com:用户名/仓库名.git

运行结果：

Cloning into '仓库名'...
remote: Enumerating objects: ...
Receiving objects: 100% ...

讲解：clone = 把远程仓库完整复制到本地（含全部历史），并自动设置好 origin。

代码案例 19.3：拉取远程更新（✅ 正确）

powershell
git pull

运行结果（远程有新提交时）：

Updating 90aca60..0546afe
Fast-forward
 app.py | 2 +-
 1 file changed

讲解：pull = fetch（下载远程提交）+ merge（合并进当前分支）。推送前先 pull——远程有新东西时不 pull 就 push 会被拒绝。

交叉验证：push 被拒绝

! [rejected]        main -> main (fetch first)
error: failed to push some refs to ...
hint: Updates were rejected because the remote contains work that you do
hint: not have locally.

讲解：报错信息已经给了解法（fetch first）。先 git pull 合并远程更新，解决可能的冲突，再 push。

04. 19.3 gitignore：哪些文件不进仓库 ▼

19.3.1 概念认知：为什么要排除文件

有些文件不该进仓库：虚拟环境（venv）、缓存（__pycache__）、密钥（API Key）、IDE 配置（.idea）——体积大、机器相关、甚至泄露机密。

代码案例 19.4：Python 项目的 .gitignore（✅ 正确）

gitignore
# 虚拟环境
venv/

# Python 缓存
__pycache__/
*.py[cod]

# 密钥（绝对不提交！）
.env
*.key

# IDE 配置
.idea/
.vscode/

# 系统文件
.DS_Store
Thumbs.db

交叉验证：不写 .gitignore 的后果

❌ 事故 1：git add . 把 venv/ 整个提交了——几千个小文件，仓库膨胀到几十 MB，队友 clone 慢到怀疑人生； ❌ 事故 2：.env 里的 API Key 被推送——密钥泄露，第三方可以刷爆你的账户（第 1 章红线：API Key 绝不入库）。

讲解：.gitignore 要在第一次 add 之前就配好——已经入库的文件，再写 .gitignore 也不会自动移出（需要用 git rm --cached，第 19 章练习）。红线：密钥文件永远在 .gitignore 里。

05. 19.4 Gitee 协作功能 ▼

19.4.1 Issue：问题与需求追踪

Issue = 仓库里的"待办/问题单"，用于：

  • 报 bug（"登录接口 500"）；
  • 提需求（"希望支持导出 Excel"）；
  • 分配任务（指派给某位成员）。

规范写法：标题一句话 + 描述"复现步骤 / 期望结果 / 实际结果"——像写验收标准一样写 Issue（第 15 章）。

19.4.2 Pull Request：代码评审的入口

Pull Request（PR）：你把你分支的改动"请求"合入主分支，合入前其他人可以评审（看 diff、提意见、讨论）。

你的分支 feature-x ──push──► 远程 feature-x
                                    │ 发起 PR
                                    ▼
                              main（评审通过后合并）

PR 是团队协作的核心流程：不是"直接 push 到 main"，而是"PR + 评审 + 合并"（第 20 章详讲）。

19.4.3 Release 与分支保护（了解）

  • Release：给某个提交打上版本号（v1.0.0），附发布说明——"正式版本"的标记；
  • 分支保护：设置"main 分支禁止直接 push，只能通过 PR 合并"——防止有人绕过评审（第 20 章工作坊启用）。

了解级边界（就业提示）：Release 与分支保护这里只要求认识；协作/发布相关岗位（DevOps、团队负责人）要求会用 Release 管理版本、用分支保护落实"评审才能合入"。面试问"怎么防止有人绕过评审"，答"开启 main 分支保护 + 只允许 PR 合并"即可。

07. 19.6 本章 Debug 四件套 ▼

问题 1：remote 已存在

问题代码：

powershell
git remote add origin git@gitee.com:...

实际报错：

fatal: remote origin already exists.

提示：origin 已经存在，怎么改地址？

讲解：用 git remote set-url origin 新地址 修改，或 git remote remove origin 后重新 add。先 git remote -v 查看当前配置。

问题 2：push 被拒绝

问题描述：git push 报 rejected（fetch first）。

提示：远程有你没有的提交，先做什么？

讲解：git pull 合并远程更新（有冲突就解决），再 push。"先拉后推"是铁律。

问题 3：把 venv 推上去了

问题描述：发现仓库里有几千个 venv 文件，clone 很慢。

提示：.gitignore 能移除已跟踪的文件吗？需要什么命令？

讲解：git rm -r --cached venv（从 Git 跟踪中移除但保留本地文件），再写 .gitignore，提交推送。教训：.gitignore 早点配。

问题 4：密钥被推上去了

问题描述：.env 文件不小心被推送，API Key 暴露。

提示：推送历史里还有密钥，只删文件够吗？

讲解：立即去 Gitee/DeepSeek 平台吊销并重新生成 Key（已泄露的 Key 视为不可信），删除文件 + git rm --cached + 提交；如需彻底清除历史需要 git filter-repo（本课程了解，老师协助处理）。红线的意思是：宁可多花 10 分钟配 .gitignore，不赌这一把。

09. 19.8 本章小结与知识树 ▼

知识树：

Gitee 平台与远程协作
├── 远程仓库：备份 / 协作 / 作品集
├── 连接方式：HTTPS（密码）vs SSH（密钥免密，推荐）
├── 常用命令
│   ├── remote add origin 地址 / remote -v 查看
│   ├── push -u origin main（首次）→ push（之后）
│   ├── clone 完整复制 / pull = fetch + merge
│   └── 铁律：先 pull 再 push
├── .gitignore：venv / __pycache__ / .env / IDE 配置
│   └── 红线：密钥绝不入库；已跟踪文件用 git rm --cached
├── Gitee 功能：Issue（问题单）/ PR（评审入口）/ Release / 分支保护
└── 作品集：README + 代码 + 提交历史 = 面试门面

必须记住的 5 件事：

  1. 先 pull 再 push，被拒绝时读报错提示；
  2. SSH 密钥配置一次，之后免密推送；
  3. .gitignore 在第一次 add 前配好；密钥文件永远排除；
  4. git rm --cached 移除已跟踪文件但保留本地；
