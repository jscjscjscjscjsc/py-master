5.1.1 当日目标

先用纯 Python 节点构建两节点 RAG 咨询图，不在第一段代码中接真实模型。学生必须先看懂状态怎样进入节点、节点返回什么更新、边怎样控制顺序。

5.1.2 第一个状态图

python
from typing import TypedDict
from langgraph.graph import END, START, StateGraph


class RagState(TypedDict):
    question: str
    evidence: list[str]
    answer: str


def retrieve(state: RagState) -> dict:
    fake_knowledge = {
        "年假": "员工转正后按制度获得相应年假。",
        "报销": "报销申请需附有效票据。",
    }
    evidence = [text for keyword, text in fake_knowledge.items() if keyword in state["question"]]
    return {"evidence": evidence}


def generate(state: RagState) -> dict:
    if not state["evidence"]:
        return {"answer": "当前知识库中没有足够依据。"}
    return {"answer": f"依据知识库：{state['evidence'][0]}"}


builder = StateGraph(RagState)
builder.add_node("retrieve", retrieve)
builder.add_node("generate", generate)
builder.add_edge(START, "retrieve")
builder.add_edge("retrieve", "generate")
builder.add_edge("generate", END)
graph = builder.compile()

result = graph.invoke({"question": "报销需要什么？", "evidence": [], "answer": ""})
print(result["answer"])

逐层解释：

  1. RagState 是整个图共享的数据契约。
  2. 节点读取完整 state，但只返回自己负责更新的字段。
  3. START 和 END 是特殊节点，标记输入和终止。
  4. compile() 在运行前检查图结构，并生成可调用对象。
  5. 线性图目前不比普通函数更简单，它的价值会在分支、恢复和观测加入后出现。

两种正确做法：

做法写法适用
做法 1（最直观）节点自己合并：return {"logs": [*state["logs"], "B 执行了"]}简单场景
做法 2（推荐）给字段声明 reducer：logs: Annotated[list[str], operator.add]框架自动合并

选择依据写在图上，值得逐字读：计数/列表累加这类「天然追加」的语义用 reducer（写法简单、不容易忘），而「谁最后写谁说了算」的字段（如 answer、final_status）就保持覆盖语义——给它加 reducer 反而是错的，会得到多条答案拼在一起的怪结果。reducer 与覆盖语义的选择，本质是「这个字段的业务语义是累加还是替换」。

（3）stream 的两种模式。 验收表记录了 stream updates（每步只吐变更字段，用于调试）与 stream values（每步吐完整状态）的实际行为差异。

5.2.1 从线性图到条件图

先增加证据质量判断：足够则生成，不足则改写问题后再检索；最大重试次数写入 state。

⚠️ 本节需要两个新节点函数。原课件 v1.0 在下面的图定义里调用了 retrieve_retry 和 generate_retry，但全章从未定义它们 （5.1 节只有签名是 RagState 的 retrieve / generate）。 这是审校发现的阻断级缺陷 —— 学生照抄会在 add_node 处直接 NameError。 完整定义如下。

python
from typing import Literal, TypedDict

from langgraph.graph import END, START, StateGraph


class RetryState(TypedDict):
    question: str
    rewritten_question: str
    evidence: list[str]
    answer: str
    retries: int
    max_retries: int


# 复用第 3 章的检索器（依赖注入，不把解析/切块代码复制进来）
def retrieve_retry(state: RetryState) -> dict:
    """检索节点。注意：要优先使用改写后的问题。"""
    # 若已经改写过问题，就用改写版；否则用原问题
    query = state.get("rewritten_question") or state["question"]
    rows = retriever.search(query, top_k=5)
    return {"evidence": [row["text"] for row in rows]}


async def generate_retry(state: RetryState) -> dict:
    """生成节点：只依据证据回答，证据不足时明确拒答。"""
    if not state["evidence"]:
        return {"answer": "当前知识库中没有足够依据。"}
    context = "\n\n".join(state["evidence"])
    result = await llm.chat([
        {"role": "system", "content": "只依据证据回答，依据不足时拒答。"},
        {"role": "user", "content": f"证据：\n{context}\n\n问题：{state['question']}"},
    ])
    return {"answer": result.text}


def route_after_retrieve(state: RetryState) -> Literal["generate", "rewrite", "give_up"]:
    if state["evidence"]:
        return "generate"
    if state["retries"] < state["max_retries"]:
        return "rewrite"
    return "give_up"


def rewrite(state: RetryState) -> dict:
    simplified = state["question"].replace("请问", "").strip()
    return {"rewritten_question": simplified, "retries": state["retries"] + 1}


def give_up(state: RetryState) -> dict:
    return {"answer": "多次检索仍没有足够依据。"}

注意 generate_retry 是 async 的（它调用异步 LLM 客户端）， 而其他节点是同步的。LangGraph 允许混用，但驱动方式有区别： 含异步节点的图要用 await graph.ainvoke(...) 或 async for ... in graph.astream(...)。 这一点在 5.5.4 节会再强调一次 —— 忘了加 await 是最常见的错误。

python
builder = StateGraph(RetryState)
builder.add_node("retrieve", retrieve_retry)
builder.add_node("rewrite", rewrite)
builder.add_node("generate", generate_retry)
builder.add_node("give_up", give_up)
builder.add_edge(START, "retrieve")
builder.add_conditional_edges(
    "retrieve",
    route_after_retrieve,
    {"generate": "generate", "rewrite": "rewrite", "give_up": "give_up"},
)
builder.add_edge("rewrite", "retrieve")
builder.add_edge("generate", END)
builder.add_edge("give_up", END)

循环的安全边界仍由程序控制。max_retries 不能只写在提示词里。

Checkpoint 在每个步骤保存 state 快照，thread_id 指向一条运行历史。InMemorySaver 只适合课堂演示（进程退出即丢失）；生产系统应使用持久化 checkpointer（见 5.2.4），并设计 thread 的用户隔离、过期和清理策略。

InMemorySaver vs 持久化 checkpointer 的差别：

InMemorySaverSqliteSaver 等持久化方案

课堂上的演示技巧：先用 InMemorySaver 演示中断/恢复（快、无依赖）， 再故意把进程关掉，重新启动后尝试恢复 —— 学生会看到恢复失败。 这个失败演示比直接讲"应该用持久化"有效得多。 5.2.4 节给出持久化版本。

5.2.3 人工审批节点

python
from langgraph.types import Command, interrupt


class ApprovalState(TypedDict):
    request: str
    draft: str
    approved: bool | None
    status: str


def make_draft(state: ApprovalState) -> dict:
    return {"draft": f"待执行方案：{state['request']}", "status": "waiting_approval"}


def approval(state: ApprovalState) -> Command[Literal["execute", "cancel"]]:
    decision = interrupt({"question": "是否批准执行？", "draft": state["draft"]})
    approved = bool(decision)
    return Command(update={"approved": approved}, goto="execute" if approved else "cancel")


def execute(state: ApprovalState) -> dict:
    return {"status": "executed"}


def cancel(state: ApprovalState) -> dict:
    return {"status": "cancelled"}
python
approval_builder = StateGraph(ApprovalState)
approval_builder.add_node("make_draft", make_draft)
approval_builder.add_node("approval", approval)
approval_builder.add_node("execute", execute)
approval_builder.add_node("cancel", cancel)
approval_builder.add_edge(START, "make_draft")
approval_builder.add_edge("make_draft", "approval")
approval_builder.add_edge("execute", END)
approval_builder.add_edge("cancel", END)
approval_graph = approval_builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "approval-001"}}
paused = approval_graph.invoke(
    {"request": "发布知识库更新", "draft": "", "approved": None, "status": "new"},
    config=config,
)
resumed = approval_graph.invoke(Command(resume=True), config=config)

关键规则：

  • interrupt() 需要 checkpointer 和 thread_id。
  • 恢复时使用同一个 thread_id。
  • 中断恢复后，包含 interrupt() 的节点会从头重新执行；中断前的副作用必须幂等。
  • 不要用普通 try/except 吞掉框架用于中断的控制异常。
  • 写操作应放在审批通过后的独立节点。

运行验证：人工审批与幂等

!人工审批的真实输出：批准路径走 Command(resume=True)→execute、拒绝路径走 cancel（execute 从未执行），同一 request_id 的重放幂等（外部只发布 1 次），以及「interrupt 之前的副作用会被重放」这一陷阱的实测（副作用被触发 2 次）

这张图里有本日最反直觉的一条实测结论，比验收通过更重要：

（1）两条路径都正确。 批准路径 Command(resume=True) → execute；拒绝路径 Command(resume=False) → cancel，而且拒绝时 execute 节点一次都没执行——图上强调了证据：「拒绝时的新息是最后一行，从未出现在已发布列表里」。这说明 execute 节点真的从未被调度，而不是"执行了又被撤销"。

（2）幂等保护：同一 request_id 重复恢复不重复执行副作用。 这里把「重复」分成两种，必须分开讨论：

情形场景结果
(a) 同一 thread 再次 resume图已结束，再次 resumestatus='executed:pub-1625d3513715'，外部发布调用次数增量 0——框架层安全
(b) 同一 request_id 换新 thread 重走审批用户重复提交 / 消息队列重复投递重走审批两次，但外部只发布 1 次，publication_id 完全相同

图上的关键结论值得原样背下来：

同一个 request_id 走了两条不同的 thread、被批准了两次，但外部系统「只被真正发布了一次」（publication_id 完全相同，未产生第二条记录）。这就是幂等键的价值——它把「业务意图的唯一性」和「执行次数的唯一性」绑定在一起。单纯依赖框架的 checkpoint 是挡不住情况 (b) 的，因为那是两个独立 thread。

（3）一个必须亲眼看到的陷阱：interrupt() 之前的副作用会被重放。 实测数据：挂起后外部副作用已被触发 1 次，恢复后累计被触发 2 次 → 变成 2 次。原因写在图上：

恢复时包含 interrupt() 的节点从头重新执行，interrupt() 之前那行代码又跑了一遍。课件 5.2.3 提醒的正是这件事，但只有亲手跑一遍才会真正记住。

正确做法三条，按可靠性排序：

  1. 结构上隔离：把副作用放到 interrupt() 之后的独立节点（本项目的 execute 节点就是这样）；
  2. 幂等键兜底：副作用函数自己用业务键去重（simulated_publish_once）；
  3. 别用 try/except 吞掉中断异常：interrupt() 靠抛异常实现挂起，被 except Exception 捕获后图就无法正确中断了（课件 5.2.3 最后一条规则）。

Day22 下半场交付：带人工审批、可恢复、副作用幂等的状态图。

截图末尾的答辩题也值得提前准备：「interrupt 为什么可能导致节点前半段代码重新执行？」答案要点是——interrupt() 的实现方式是抛异常来中断当前节点执行，恢复时框架并不知道上次执行到哪一行（也不打算做行级恢复），它选择最简单可靠的策略：把整个节点重新跑一遍。所以节点必须设计成「重放安全」：纯计算放前面，副作用放后面或做成幂等。这不是框架的缺陷，而是分布式系统里「至少一次执行」语义的必然结果。

5.2.4 持久化 checkpointer：跨进程恢复

为什么必须讲这一节：原课件 v1.0 在依赖清单里列了 langgraph-checkpoint-sqlite， 但正文没有任何持久化代码，只在讲解里写了句"生产系统应使用"。 而 5.2.4 的验收标准第 4 条恰好要求"进程重启后仍可恢复"—— 用 InMemorySaver 是不可能通过这条验收的。这一节补上实现。

安装：

powershell
pip install langgraph-checkpoint-sqlite

用法（与 InMemorySaver 的接口完全一致，只换构造方式）：

python
import sqlite3
from pathlib import Path

from langgraph.checkpoint.sqlite import SqliteSaver


Path("storage").mkdir(parents=True, exist_ok=True)
conn = sqlite3.connect("storage/checkpoints.db", check_same_thread=False)

# SqliteSaver 与 InMemorySaver 是同一个 Checkpointer 接口的两个实现，
# 所以下面的代码与 5.2.2 完全一样 —— 这就是抽象的价值。
with SqliteSaver(conn) as checkpointer:
    graph = approval_builder.compile(checkpointer=checkpointer)

    config = {"configurable": {"thread_id": "approval-002"}}
    # 停在中断点。（注意：字典字面量里不能写 "..." 占位符，
    # 那会让它变成非法的 set/dict 混合语法 —— 这里必须给完整字段。）
    graph.invoke(
        {"request": "发布知识库更新", "draft": "", "approved": None, "status": "new"},
        config=config,
    )
    # ← 此时把进程关掉，重新启动，checkpointer 换成同一个 db 文件
    # graph.invoke(Command(resume=True), config=config)  ← 仍能恢复

跨进程验证方法（这是本节的验收方式）：

powershell
# 进程 1：跑到中断点，然后退出
python code/ch05/22_persistence.py --start

# 进程 2：全新进程，从同一个 db 恢复
python code/ch05/22_persistence.py --resume

⚠️ 只在一个进程里验证恢复是无效的。 因为 InMemorySaver 在同一个进程里也能"恢复"——你无法证明它真的落盘了。 必须用两个独立进程，进程 2 启动时对进程 1 的内存一无所知。 这个原则和 Day19 的 SQLite 记忆验证是同一个：验证持久化，必须换进程。

运行验证：跨进程恢复：

powershell
python code/ch05/22_persistence.py --start    # 进程 1：跑到中断点后退出
python code/ch05/22_persistence.py --resume   # 进程 2：从同一个 db 恢复

这张图是本日最硬的一条证据——恢复发生在另一个进程里：

（1）跨进程恢复真的发生了。 终端明确标注：「两个子进程都已退出，上面的中断来自进程 1，恢复来自进程 2」，恢复后 approved=True、executed_count=1、最终 next=()（空，已结束）。这才是 SqliteSaver 与 MemorySaver 的分水岭：

中断发生在上一个进程，恢复发生在这个进程 —— 如果用的是 MemorySaver，这一步会找不到 thread（状态已随进程消失）。

（2）checkpoint 表结构——「框架帮你存了状态」不是黑盒魔法。 图上直接打印了 SQLite 里的表结构：checkpoints 5 行、writes 18 行，并列出 checkpoints 表的实际列（thread_id, checkpoint_ns, checkpoint_id, parent_checkpoint_id, type, checkpoint, metadata）。最新一条记录显示 parent_checkpoint_id 指向父记录——形成链，所以能回潮历史。

图上有一段话建议原样讲给学生：

学生第一次见到「框架帮我存了状态」时，往往把它当黑盒魔法。打开表看一眼就知道它无非是 [thread_id + checkpoint_id + 父指针 + 序列化状态] —— 和你自己写一张状态表没有本质区别，只是它把版本链和并发控制做对了。

（3）thread 隔离是默认行为。 图里对比了 workflow-persist-001（有状态）与 workflow-persist-OTHER（无状态）的差异：thread_id 是 checkpoint 的分区键。图上同时指出生产环境要补的三件事：权限（拿到 thread_id 就能读状态，接口层必须校验归属，不能只靠猜不到）、过期清理（按业务保留期删除，否则 SQLite 会无限增长）、换存储（多实例部署要换 PostgresSaver，否则两个实例各写各的文件，恢复行为会变得不可预测）。

验收表对应 5.2.5 的第 4 条：「SqliteSaver 跨进程恢复——进程 1 中断退出，进程 2 恢复并批准成功」。

生产环境的 checkpointer 选型：

方案适用
InMemorySaver课堂演示、单元测试
SqliteSaver单机部署、中小规模
Postgres / Redis checkpointer多实例部署（状态必须共享）

选型的关键问题：「我的服务会跑几个实例？」 多实例时，同一个 thread 的请求可能落到不同实例上， 所以状态必须存在所有实例都能访问的地方。 这和 MCP 无状态化（第 6 章 Day27）要解决的是同一类问题—— 状态放在哪里，决定了你能怎么部署。

04. 5.3 Day 23｜CrewAI 与 smolagents：两种不同抽象 ▼

5.3.1 为什么在主线之外学习对照框架

对照的目的不是记 API，而是识别抽象差异：LangGraph 强调显式状态与控制流，CrewAI 强调角色、任务和团队，smolagents 提供工具调用 Agent 与代码 Agent。

5.3.2 CrewAI 三角色写作流水线

⚠️ 必须先配置模型，否则一定失败（原课件 v1.0 的阻断级缺陷）： v1.0 的 Agent(...) 没有传 llm= 参数。CrewAI 在缺省情况下会默认去连 OpenAI， 也就是需要 OPENAI_API_KEY 环境变量。按本课程（靶场 / DeepSeek / 通义）配置的环境， 直接运行会报认证失败 —— 学生无法开课。

正确做法：显式构造 LLM 并传给每个 Agent。

python
import os

# ⚠️ 必须在 import crewai 之前关闭遥测：CrewAI 首次运行会弹遥测提示并尝试外连，
#    课堂网络受限时会卡住。（实测：CrewAI 1.15.22）
os.environ["CREWAI_TRACING_ENABLED"] = "false"

from crewai import LLM, Agent, Crew, Process, Task

# CrewAI 的 LLM 类接受 OpenAI 兼容的参数，可以直接指向靶场或任意平台。
llm = LLM(
    # ⚠️ 实测坑：model 必须带 provider 前缀。
    #    写 "mock-chat" 会报 "LLM Provider NOT provided"，必须写 "openai/mock-chat"。
    #    前缀告诉 CrewAI 用哪个 provider 适配器。
    model=f"openai/{os.getenv('LLM_CHAT_MODEL', 'mock-chat')}",
    base_url=os.getenv("LLM_BASE_URL", "http://127.0.0.1:8100/v1"),
    api_key=os.getenv("LLM_API_KEY", "mock-key"),
    temperature=0.3,
)

researcher = Agent(
    role="资料研究员",
    goal="从给定资料中提取可核查事实",
    backstory="你只使用允许的资料工具，并保留来源。",
    llm=llm,                    # ← 三个 Agent 都要传
    allow_delegation=False,
    verbose=True,
)

writer = Agent(
    role="技术写作者",
    goal="把研究结果写成结构清晰的中文说明",
    backstory="你区分事实、解释和建议，不添加无来源数字。",
    llm=llm,
    allow_delegation=False,
    verbose=True,
)

editor = Agent(
    role="审校员",
    goal="检查逻辑、引用和格式，输出最终稿",
    backstory="发现证据不足时退回，不自行补造事实。",
    llm=llm,
    allow_delegation=False,
    verbose=True,
)

research_task = Task(description="研究主题：{topic}，输出事实清单与来源。", expected_output="Markdown 事实表", agent=researcher)
writing_task = Task(description="依据研究结果撰写 800 字说明。", expected_output="包含标题、正文和引用的 Markdown", agent=writer, context=[research_task])
review_task = Task(description="审查文章并输出修订后的最终稿。", expected_output="通过审校的 Markdown", agent=editor, context=[research_task, writing_task])

crew = Crew(
    agents=[researcher, writer, editor],
    tasks=[research_task, writing_task, review_task],
    process=Process.sequential,
    verbose=True,
)

result = crew.kickoff(inputs={"topic": "企业知识库如何减少无依据回答"})

讲解重点：

  • 角色不等于三个不同模型：角色主要是不同目标、上下文和工具权限。三个 Agent 共用同一个
  • context 明确任务依赖，Process.sequential 明确顺序；
  • Process 有两种取值：sequential（顺序）与 hierarchical（层级）。
  • 应分别保存中间产物，才能判断错误来自研究、写作还是审校。

版本提示（实测版本，核实日期 2026-09-21）：

框架实测版本需要注意的 API 差异
langgraph1.2.12stream(version="v2") 可用（需 ≥1.1）；Command / interrupt 在 langgraph.types
langgraph-checkpoint4.2.0—
langgraph-checkpoint-sqlite3.1.1只有 SqliteSaver，没有 AsyncSqliteSaver

关于「用靶场跑框架」的诚实说明

本课程的对照组（CrewAI / smolagents）接的是离线靶场，而靶场是关键词驱动的确定性桩模型， 不具备真实模型的 ReAct 结构化输出能力。这会带来两个可观察的差异，授课时必须向学生说明：

现象原因怎么解读
CrewAI 三个 Task 的产出质量不高（都是桩模型的 JSON 抽取模板）桩模型不产出 Thought / Final Answer 结构化输出链路正确性已验证（无 401、不外连 OpenAI、3 个 Task 全部跑完）。产出质量取决于真实模型 —— 换成真实平台后质量会正常
smolagents 会一直循环到 max_steps桩模型把上一轮 Observation（含关键词）当作新输入，反复调用同一工具由框架的 max_steps 兜住，这恰好演示了「为什么必须有步数上限」

教学价值：这两个现象不是"缺陷"，而是很好的教学素材。 它们直观展示了「Agent 框架的行为高度依赖底层模型的能力」—— 换个模型，同一份代码的表现可以完全不同。 这也是第 5 章要讲「框架选型」而不是「框架崇拜」的原因。

验收方式：对照组实验验收看链路与日志（工具是否被调用、消息列表是否正确、 有没有触发步数上限），不要看桩模型的措辞质量。要评估产出质量请切到真实平台。

5.3.3 smolagents 工具定义

⚠️ 原课件 v1.0 的缺陷：下面的例子用了 model=configured_model， 但configured_model 是一个从未定义的占位符，运行会直接 NameError。 这里补上完整的模型构造方式。

python
import os

from smolagents import OpenAIServerModel, ToolCallingAgent, tool


# smolagents 用 OpenAIServerModel 接任意 OpenAI 兼容端点
configured_model = OpenAIServerModel(
    model_id=os.getenv("LLM_CHAT_MODEL", "mock-chat"),
    api_base=os.getenv("LLM_BASE_URL", "http://127.0.0.1:8100/v1"),
    api_key=os.getenv("LLM_API_KEY", "mock-key"),
)


@tool
def policy_search(question: str) -> str:
    """查询企业制度知识库。

    Args:
        question: 需要查询的完整制度问题。
    """
    result = rag_pipeline.answer(question)
    return result.answer


agent = ToolCallingAgent(
    tools=[policy_search],
    model=configured_model,      # ← 现在它是真实的对象了
    max_steps=6,
)

answer = agent.run("查询差旅制度并概括住宿报销要求")

如果 OpenAIServerModel 不可用：smolagents 也支持 LiteLLMModel（走 LiteLLM 网关） 和 InferenceClientModel（走 Hugging Face Inference）。 三者都是同一个 Model 接口的实现，换起来只改构造那几行。 具体可用的类名以你安装的版本为准 —— 这个库迭代很快。

装饰器依赖函数类型标注和包含 Args 的 docstring 来生成工具描述 （与第 7 章我们要自研的 @tool 装饰器是同一个设计思路）。 configured_model 由配置模块按课堂所选供应商创建，不在业务代码中硬编码密钥。

5.5.1 项目任务

实现“需求分析 → 检索资料 → 生成方案 → 自动审校 → 人工审批 → 执行或退回”的流程。执行节点先使用无副作用的模拟发布工具，避免课堂误触真实系统。

flowchart TD
    A[analyze] --> B[research]
    B --> C[draft]
    C --> D[review]
    D -->|需修改且未超限| C
    D -->|达到修改上限| X[fail]
    D -->|通过| E[approval]
    E -->|批准| F[execute]
    E -->|拒绝| G[cancel]
    F --> H[END]
    G --> H
    X --> H

5.5.2 状态设计

python
from typing import Literal, TypedDict


class WorkflowState(TypedDict):
    request: str
    requirements: list[str]
    evidence: list[dict]
    draft: str
    review_status: Literal["pending", "revise", "pass", "fail"]
    review_notes: list[str]
    revision_count: int
    max_revisions: int
    approved: bool | None
    final_status: str
    request_id: str

状态只保存恢复流程所需的信息。大文件、密钥和连接对象放外部存储或运行时依赖，不写进 checkpoint。

5.5.3 核心节点

python
def analyze(state: WorkflowState) -> dict:
    requirements = [item.strip() for item in state["request"].split("，") if item.strip()]
    return {"requirements": requirements, "final_status": "analyzed"}


def research(state: WorkflowState) -> dict:
    rows = retriever.search(state["request"], top_k=5)
    return {"evidence": rows, "final_status": "researched"}


async def draft(state: WorkflowState) -> dict:
    evidence_text = "\n".join(row["text"] for row in state["evidence"])
    prompt = f"需求：{state['requirements']}\n证据：{evidence_text}\n请生成可执行方案并标注证据。"
    result = await llm.chat([{"role": "user", "content": prompt}])
    return {"draft": result.text, "final_status": "drafted"}


def review(state: WorkflowState) -> dict:
    notes: list[str] = []
    if not state["evidence"]:
        notes.append("缺少检索证据")
    if len(state["draft"].strip()) < 100:
        notes.append("方案内容过短")
    next_count = state["revision_count"] + (1 if notes else 0)
    if notes and next_count > state["max_revisions"]:
        status = "fail"
    else:
        status = "revise" if notes else "pass"
    return {"review_notes": notes, "review_status": status, "revision_count": next_count}


def approval(state: WorkflowState) -> Command[Literal["execute", "cancel"]]:
    decision = interrupt({
        "request_id": state["request_id"],
        "draft": state["draft"],
        "review_notes": state["review_notes"],
    })
    approved = bool(decision)
    return Command(update={"approved": approved}, goto="execute" if approved else "cancel")


def execute(state: WorkflowState) -> dict:
    publication_id = simulated_publish_once(state["request_id"], state["draft"])
    return {"final_status": f"executed:{publication_id}"}


def cancel(state: WorkflowState) -> dict:
    return {"final_status": "cancelled"}


def fail(state: WorkflowState) -> dict:
    return {"final_status": "review_failed"}

审校节点先使用确定性规则，方便测试。提高项再加入模型评审，但不能删除规则检查和修改次数上限。

幂等发布：simulated_publish_once 的实现

原课件 v1.0 的缺陷：execute 节点调用了 simulated_publish_once， 但全章没有定义这个函数（运行必 NameError）。 而它恰恰是"幂等测试"评分项的基础 —— 缺了它，这道评分项无法完成。 实现如下。

python
import hashlib

# 记录已发布的 request_id → publication_id。
# 生产环境这个"记录"应该在数据库里（或直接依赖下游系统的幂等键），
# 课堂用内存字典即可，但要理解：内存版在多实例部署下会失效。
_PUBLISHED: dict[str, str] = {}


def simulated_publish_once(request_id: str, draft: str) -> str:
    """幂等的模拟发布：同一 request_id 重复调用只产生一个 publication_id。

    为什么需要幂等：审批恢复时，包含 interrupt() 的节点会从头重新执行，
    而且用户可能重复点击"批准"。如果没有幂等保护，
    同一次发布会被执行多次（真实场景里就是重复发邮件、重复扣款）。
    """
    if request_id in _PUBLISHED:
        # 已发布过，直接返回原来的 id —— 这就是幂等
        return _PUBLISHED[request_id]

    publication_id = "pub_" + hashlib.md5(
        f"{request_id}:{draft}".encode("utf-8")
    ).hexdigest()[:12]
    _PUBLISHED[request_id] = publication_id
    print(f"    [已发布] request_id={request_id} → {publication_id}")
    return publication_id

幂等的三种实现层次（答辩会被追问）：

层次做法适用
应用层去重像上面这样用 request_id 记表课堂、单实例
数据库唯一约束给 request_id 加 unique 索引，重复插入直接失败生产主流做法
下游系统幂等键把幂等键透传给支付/消息系统，由它保证调用第三方 API 时唯一可靠的做法

越靠下游越可靠。如果下游支持幂等键，优先用它 —— 因为应用层崩溃时你的记录可能丢， 但下游的记录不会。

5.5.4 路由与编译

python
def route_review(state: WorkflowState) -> Literal["draft", "approval", "fail"]:
    return {"revise": "draft", "pass": "approval", "fail": "fail"}[state["review_status"]]


builder = StateGraph(WorkflowState)
for name, node in {
    "analyze": analyze,
    "research": research,
    "draft": draft,
    "review": review,
    "approval": approval,
    "execute": execute,
    "cancel": cancel,
    "fail": fail,
}.items():
    builder.add_node(name, node)

builder.add_edge(START, "analyze")
builder.add_edge("analyze", "research")
builder.add_edge("research", "draft")
builder.add_edge("draft", "review")
builder.add_conditional_edges("review", route_review, {"draft": "draft", "approval": "approval", "fail": "fail"})
builder.add_edge("execute", END)
builder.add_edge("cancel", END)
builder.add_edge("fail", END)
workflow = builder.compile(checkpointer=InMemorySaver())

approval 使用 Command(goto=...) 动态路由，因此不要再为该节点添加会重复执行的静态出边。

完整初值字典（必填，缺一个字段就会 KeyError）

原课件 v1.0 的缺陷：下面这行调用里用了 initial_state， 但全章从未给出它的定义。WorkflowState 有 11 个字段， 而 LangGraph 的 TypedDict state 没有默认值 —— 访问未初始化的键会直接 KeyError。 这是一个"看起来只差一行、实际完全跑不起来"的缺口。

python
import uuid

initial_state: WorkflowState = {
    "request": "为知识库问答系统增加引用溯源能力，并控制单次回答的成本",
    "requirements": [],
    "evidence": [],
    "draft": "",
    "review_status": "pending",
    "review_notes": [],
    "revision_count": 0,
    "max_revisions": 2,          # 关键：修改上限，防止 review↔draft 无限循环
    "approved": None,
    "final_status": "new",
    "request_id": uuid.uuid4().hex,   # 幂等键，execute 节点靠它去重
}

初始化 state 的三条经验：

  1. 所有字段都要给初值，包括空列表与 None。不要指望"节点会填"——
  2. 安全边界类的字段（如 max_revisions）必须在初始状态里定死，
  3. request_id 在进入图之前生成，而不是在 execute 节点里生成 ——

运行与恢复：由于 draft 是异步节点，运行流程时使用 await workflow.ainvoke(initial_state, config=config)，恢复时使用 await workflow.ainvoke(Command(resume=True), config=config)。

⚠️ 最容易犯的错误：忘了 await。 async def 节点必须用 ainvoke / astream 驱动，用同步的 invoke 会报错 （或者拿到一个未被 await 的协程对象，表现为"什么都没发生"）。 排查技巧：如果图"跑了但没有输出"，第一件事就是检查 await 和 invoke/ainvoke 是否配对。

5.5.6 最终演示顺序

  1. 正常请求运行到审批中断，展示 checkpoint 和 thread_id。
  2. 批准后恢复并模拟发布，展示最终状态。
  3. 拒绝另一请求，确认 execute 节点没有运行。
  4. 注入空证据，展示审校退回和修改上限。
  5. 对同一 request_id 重复恢复，展示幂等保护。
  6. 输出 updates、checkpoints 或任务事件，按节点解释耗时和失败。

07. 5.6 常见错误与排查顺序 ▼
现象优先检查修复原则
state 字段突然丢失节点返回的是部分更新还是错误地重建全 state明确 reducer 与覆盖语义
图无法结束是否存在无退出条件的回边计数器、预算和 END 路径写进图
中断后不能恢复是否配置 checkpointer；thread_id 是否一致将恢复标识视为数据契约
恢复后副作用执行两次副作用是否放在 interrupt 前；是否有幂等键审批与执行拆节点
CrewAI 中间错误难定位是否保留每个 Task 产物分阶段评测，不只看最终稿
CodeAgent 越权执行器是否能访问主机文件与网络使用最小权限沙箱
框架升级后示例报错是否混用不同版本文档查锁定版本 API，不盲目改业务逻辑
