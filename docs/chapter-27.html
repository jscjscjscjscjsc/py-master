02. 27.1 大模型能做什么、不能做什么 ▼

27.1.1 概念认知：LLM 是什么

大语言模型（LLM） 本质上是一个"超级文本预测器"：根据前文预测下一个最可能的词，一个词一个词地"写"出回答。DeepSeek、GPT、Claude 都是 LLM。

27.1.2 能做：四大强项

能力例子
文本生成写文章、写邮件、写代码
理解与总结总结会议纪要、提炼要点
翻译与改写中英互译、改写语气
问答与推理解释概念、分析问题

27.1.3 不能做：能力边界（关键认知）

❌ 边界 1：幻觉（Hallucination）——模型可能一本正经地编造不存在的事实。"它说得流畅 ≠ 它说得对"。

❌ 边界 2：没有真实记忆——每次调用只"记得"你传入的 messages，关掉就忘。所谓"记忆"是你把历史对话传回给它的。

❌ 边界 3：不是计算器——"算 123456 × 789012"这类精确计算可能错。让模型算数不如写 Python 算。

❌ 边界 4：不能自主行动——它只会"输出文字"，不会自己点按钮、发请求、操作文件——除非你用代码帮它调用工具（这就是第 28 章工具调用、第 29 章智能体框架要解决的）。

交叉验证：把大模型当"搜索引擎/计算器"的错误用法

❌ 错误用法 1："帮我查一下 2026 年世界人口"——模型没有实时数据，可能编一个； ❌ 错误用法 2："算一下 2 的 100 次方"——直接写 Python 更可靠； ✅ 正确用法：让模型"解释概念、起草内容、拆解任务"，把"需要精确/实时/行动"的事交给代码和工具。

就业提示：面试"大模型的局限性"——答幻觉、无记忆、无实时数据、不能行动，这四点就是标准答案。

03. 27.2 API 调用原理 ▼

27.2.1 概念认知：为什么用 API

回顾原教材（Vibe Coding 实战）3.1 节：不用自己训练模型，通过 API 按规则发请求就能获得模型能力——API 是"大模型的公共电话线"。

27.2.2 语法掌握：一次请求的结构

代码案例 27.1：请求骨架（✅ 正确）

json
POST https://api.deepseek.com/chat/completions

{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "system", "content": "你是 Python 学习助手"},
    {"role": "user", "content": "解释什么是装饰器"}
  ],
  "temperature": 0.7,
  "max_tokens": 400
}

讲解：

  • model：用哪个模型（DeepSeek 的 deepseek-v4-flash 推理型 / deepseek-chat 通用对话；模型名以官网为准）；
  • messages：对话历史（大模型的"记忆"全在这里）；
  • temperature：随机性（0 严谨、1 发散）；
  • max_tokens：最多输出多少 token——也是控制成本的关键参数。

27.2.3 原理探秘：messages 的三个角色

system   系统指令：设定角色与规则（"你是客服，语气亲切"）
user     用户消息：你说了什么
assistant 模型消息：模型之前说了什么（多轮对话时把历史传回去）

多轮对话的原理：每次请求都带上完整历史（messages 数组），模型才能"记得"之前的内容——上下文窗口（context window）就是 messages 能装多少内容的限制。

微任务卡（M1 · 讲解卡 · L3）：把请求骨架发给 AI："请解释 system/user/assistant 三个角色的区别，以及为什么多轮对话要把历史全部传回去。"一句话记录理解。

04. 27.3 智能体（Agent）：让大模型"动起来" ▼

27.3.1 概念认知：Agent 四要素

智能体（Agent）= LLM（大脑）+ 规划 + 工具 + 记忆：

感知：接收用户需求 / 外部信息
规划：把任务拆成步骤（LLM 负责）
工具：执行具体动作（查待办、算数、发请求——代码写的函数）
反思：根据结果判断下一步（LLM 负责）

案例 27.2：用 Codex 演示"拆解任务"

给 AI 一个模糊任务："帮我安排周末旅行"，观察它如何拆解：

1. 确定目的地与预算（需要用户提供）
2. 查交通（工具：车票/机票查询）
3. 查住宿（工具：酒店 API）
4. 生成行程（LLM 能力）
5. 汇总成清单（输出）

讲解：LLM 负责"想"（规划、拆解、判断），工具负责"做"（查询、计算、执行）——这就是智能体的核心分工。你自己写代码时也是这样：让 AI 生成代码（想），你用代码跑（做），验证结果（反思）。

27.3.2 原理探秘：为什么 LLM 不能"自己行动"

LLM 的输出只是文本。"查天气"这个动作，模型不会做——它只能"说"出"我应该查天气"。工具调用（Function Calling） 让模型输出"我要调用 query_weather 函数，参数是北京"这样的结构化指令，你的代码执行函数、把结果传回模型，模型再基于结果继续回答——这一来一回，就是智能体的"手脚"（第 28 章手把手实现）。

微任务卡（M2 · 对比卡 · L3）：把"LLM 输出"与"工具执行"两类行为发给 AI："请对比模型'说'查天气和代码'真'查天气的区别，说明为什么智能体必须两者结合。"一句话记录理解。

05. 27.4 MCP：工具互联标准（了解） ▼

MCP（Model Context Protocol，模型上下文协议） 是 2024 年底提出的开放标准：让 AI 应用以统一方式连接外部工具和数据源——就像 USB-C 统一了充电接口。

没有 MCP：每个工具一套接入方式（每家 AI 连数据库、文件、API 各写各的）
有了 MCP：工具提供"标准插口"，任何支持 MCP 的 AI 直接插上就能用

讲解：本课程了解概念即可——你第 28 章手写的"工具调用"就是 MCP 要标准化的那个场景。

了解级边界（就业提示）：MCP 了解即可；但面试问"AI 应用怎么连接外部工具"时，能说出"工具调用 + MCP 标准化"就是加分项——第 28 章手写的工具调用，正是 MCP 要标准化的场景。

06. 27.5 本章 Debug 四件套（概念类） ▼

问题 1：把幻觉当事实

问题描述：模型说"Python 3.13 已发布"，你直接写进报告——结果版本号是编的。

讲解：凡是"精确事实"都要验证。让模型给出处、或用可靠来源核对；不确定就标注"待核实"。

问题 2：把模型当实时数据源

问题描述："今天上海天气怎么样？"模型答了一个编的天气。

讲解：模型没有实时数据。实时信息必须走工具/API（天气接口、数据库）——这正是智能体要接工具的原因。

问题 3：单轮对话"失忆"

问题描述：第二轮问"我上一轮说了什么"，模型答不上来。

讲解：模型没有记忆，记忆 = 你传回的 messages 历史。多轮对话必须维护并传回历史数组。

问题 4：让它"自己去做"

问题描述："帮我把文件保存到桌面"——模型回答"好的，已保存"，但文件根本没保存。

讲解：模型只能输出文字。"执行"必须由代码完成：模型输出意图 → 代码执行 → 结果回传。知道这个边界，就不会被"假执行"骗到。

08. 27.7 本章小结与知识树 ▼

知识树：

大模型、API 与智能体
├── LLM = 超级文本预测器
│   ├── 能做：生成 / 理解总结 / 翻译 / 问答推理
│   └── 不能做：幻觉 / 无记忆 / 非计算器 / 不能行动
├── API 调用
│   ├── POST /chat/completions：model + messages + temperature + max_tokens
│   ├── role：system（规则）/ user（提问）/ assistant（历史）
│   └── 记忆 = 传回 messages 历史；上下文窗口 = 容量限制
├── 智能体四要素：感知 / 规划 / 工具 / 反思
│   └── LLM 负责"想"，工具负责"做"（工具调用 = 手脚）
└── MCP：工具互联标准（了解）

必须记住的 5 件事：

  1. 大模型四大边界：幻觉、无记忆、非计算器、不能行动；
  2. messages 三角色：system 定规则、user 提问、assistant 历史；
  3. 模型的"记忆"= 你传回的历史，不是它自己记住的；
  4. 智能体 = LLM（想）+ 工具（做）；
  5. 让模型"精确计算/实时查询/执行动作"之前，先想清楚：这是不是该用代码/工具做？
