03. 31.3 任务一：总体架构设计 ▼

31.3.1 设计目标

四个原则（答辩必讲）：

  1. 分层清晰：routers（HTTP）→ services（业务/AI）→ db（数据） 单向依赖，路由不写 SQL；
  2. 契约先行：API 清单先冻结，前后端并行；
  3. AI 可替换：AI 调用收敛到一个 AIService 类，测试时整体替换为假实现；
  4. 数据库独立：SQLite 访问收敛到 app/db.py，换库只改一层。

31.3.2 架构图（写进设计文档）

│ 浏览器（前端）                                          │
│  Vue 3（CDN）+ marked + highlight.js                  │
│  三栏工作区：笔记库 ｜ 编辑器/问答 ｜ AI 助手             │
└───────────────┬──────────────────────────────────────┘
                │ HTTP + JSON（REST，/api 前缀）
┌───────────────▼──────────────────────────────────────┐
│ FastAPI 后端（uvicorn，端口 8000）                      │
│  routers → services → db                              │
└───────────────┬──────────────────────────┬────────────┘
                │                          │
     SQLite（本地 notes.db）          DeepSeek API（HTTPS）

31.3.4 前端信息架构：三栏工作区

┌──────────┬─────────────────────────┬─────────────────┐
│ 笔记库     │ 编辑器 / AI 问答中心        │ AI 助手          │
│ 搜索框     │ 标题 + 标签编辑            │ 生成摘要          │
│ 标签 chips │ 左编辑 / 右预览            │ AI 建议标签        │
│ 笔记列表    │ 问答流 + 来源卡片          │ 选中文本处理       │

信息架构原则：左输入（笔记库）→ 中处理（编辑/问答）→ 右产出（AI 结果）。"边写边问"成为自然动作，而不是把 AI 藏进二级页面。

04. 31.4 任务二：数据库设计 ▼

31.4.1 ER 关系

notes ──< note_tags >── tags        （多对多）
chat_messages（独立，保存问答历史与来源快照）

31.4.2 表结构（与参考实现一致，写进设计文档）

sql
CREATE TABLE notes (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    title      TEXT NOT NULL,
    content    TEXT NOT NULL DEFAULT '',
    summary    TEXT NOT NULL DEFAULT '',      -- AI 摘要结果冗余存储
    is_pinned  INTEGER NOT NULL DEFAULT 0,    -- 0/1
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE tags (
    id    INTEGER PRIMARY KEY AUTOINCREMENT,
    name  TEXT NOT NULL UNIQUE,
    color TEXT NOT NULL DEFAULT '#4f8cff'
);

CREATE TABLE note_tags (
    note_id INTEGER NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
    tag_id  INTEGER NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
    PRIMARY KEY (note_id, tag_id)
);

CREATE TABLE chat_messages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    role       TEXT NOT NULL,               -- user / assistant
    content    TEXT NOT NULL,
    note_ids   TEXT NOT NULL DEFAULT '[]',  -- 引用的笔记 id（JSON）
    sources    TEXT NOT NULL DEFAULT '[]',  -- 来源段落快照（JSON）
    created_at TEXT NOT NULL
);

31.4.3 设计要点（答辩高频）

  1. 为什么用中间表：一篇笔记多个标签、一个标签多篇笔记，只有 note_tags 中间表能正确建模；去掉它要么数据冗余、要么查不出来；
  2. 为什么 summary 冗余存笔记表：列表页直接展示摘要，读多写少，省一次 AI 调用；
  3. 为什么时间戳用 ISO 字符串：SQLite 没有专门的 datetime 类型，ISO 可排序、可前端本地化；
  4. 为什么开外键：PRAGMA foreign_keys = ON + ON DELETE CASCADE，删笔记自动清理中间表。

微任务卡（M2 · 数据库卡 · L4）：把上面的 SQL 发给 AI："请审查表结构：有没有冗余？索引怎么加？chat_messages 的 note_ids/sources 用 JSON 字符串有什么坑？"一句话记录你的取舍。

06. 31.6 任务四：AI 接入设计 ▼

31.6.1 调用封装

AIService 统一封装 DeepSeek 兼容接口，所有业务方法只返回纯文本/结构化结果：

POST {base_url}/chat/completions
Authorization: Bearer {DEEPSEEK_API_KEY}
body: {model: "deepseek-v4-flash", messages: [...], temperature, max_tokens}

31.6.2 成本控制三件套

  1. 截断上下文：每篇笔记最多取 AI_CONTEXT_CHARS（3000 字符）、最多选 5 篇；
  2. 限制输出：摘要 max_tokens=300、建议标签 150、文本处理 600、普通问答 1024（deepseek-v4-flash 为推理型模型，max_tokens 需覆盖推理 + 回答预算）；
  3. 超时兜底：requests 强制 timeout=60；401/402 转友好提示（Key 无效 / 余额不足）。

31.6.3 提示词模板（写进设计文档）

摘要（system）：

你是一名学习笔记助手。请用中文为笔记生成一段不超过 120 字的摘要，
直接输出摘要文本，不要任何前缀、标题或解释。

问答（system）：

你是 AI 学习笔记助手，只基于用户提供的笔记回答。
要求：1) 用中文回答；2) 引用笔记时在句末标注 [1][2]，编号对应参考资料顺序；
3) 笔记中没有的内容明确说明"笔记中没有提到"，不要编造。

31.6.4 引用溯源方案（无向量库）

不做 RAG。回答后对每篇引用笔记做关键词回查：

  1. 问题拆成 2 字以上关键词；
  2. 正文按空行切段，统计每段命中数；
  3. 取命中最多的一段作为来源快照（snippet）；
  4. 前端把来源卡片与回答中的 [1][2] 角标对应。

这个方案零额外依赖、可解释、成本可控，是"9 学时能交付"的关键取舍之一。
