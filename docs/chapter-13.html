from datetime import date

birthday = date(2006, 5, 1)
today = date.today()

print(f"你已经活了 {days} 天")
print(f"今年约 {age} 岁")

运行结果（以 2026-08-06 为准）：

你已经活了 7398 天
今年约 20 岁

讲解：日期可以直接相减，结果是 timedelta 对象，.days 取天数。真实场景：计算会员到期、合同剩余天数、订单超时。

13.2.2 语法掌握：re 提取信息

代码案例 13.5：提取手机号（✅ 正确）

python
import re

text = "客服电话：13812345678，值班手机：13987654321，座机 010-12345678"

phones = re.findall(r"1[3-9]\d{9}", text)
print(phones)

运行结果：

['13812345678', '13987654321']

讲解：

  • re.findall(模式, 文本)：找出所有匹配；
  • r"1[3-9]\d{9}" 的含义：以 1 开头，第二位是 3-9，后面 9 个数字——共 11 位（大陆手机号格式）；
  • r 是原始字符串（反斜杠不转义），\d 表示数字，{9} 表示重复 9 次；
  • 座机"010-12345678"不匹配（第二位是 1，不在 3-9），正则按模式精确匹配。

原理探秘：正则的三个基础构件

  1. 字符类：\d 数字、\w 字母数字下划线、\s 空白；[3-9] 指定范围；
  2. 量词：* 0 次或多次、+ 1 次或多次、{9} 恰好 9 次；
  3. 锚点：^ 开头、$ 结尾（本章了解即可，第 13 章之前说过第 4 章是入门——这里把它用起来）。

hashlib：哈希与密码存储（✅ 正确，了解）

python
import hashlib

def hash_password(password, salt=""):
    """把密码转成固定长度的哈希值；加盐防撞库"""
    data = (password + salt).encode("utf-8")
    return hashlib.sha256(data).hexdigest()

pwd = "123456"
print(hash_password(pwd))
print(hash_password(pwd) == hash_password(pwd))          # 同一输入 → 同一输出
print(hash_password(pwd, "salt!") != hash_password(pwd)) # 加盐 → 结果不同

运行结果：

a665a45920422f9d417e4867efdc4fb8a04a1f3fff1fa07e998e86f7f7a27ae3
True
True

原理探秘：哈希为什么能保护密码？

哈希是单向函数：能算过去、不能算回来。数据库存的是"哈希值"而不是明文——即使数据库泄露，攻击者拿到的也只是哈希。加盐（salt） 是在密码后拼接一段随机字符串再哈希，让"相同密码"在不同用户处产生不同哈希，防止撞库攻击。

交叉验证：哈希 vs 加密

哈希（单向）：密码 → 哈希值，算不回去 → 用于存储密码、校验文件完整性
加密（双向）：明文 → 密文，可以解密 → 用于传输数据（如 HTTPS）

讲解：哈希不是加密——加密能解密，哈希不能。这是安全面试的经典区分题。

就业提示：后端面试必考"密码怎么存"——标准答法：绝不存明文，用加盐哈希（如 bcrypt/argon2 或 SHA-256 + 盐）。能用这个思路回答，就已经超过大多数应届生。

微任务卡（M2 · 讲解卡 · L3）：把 hashlib 加盐代码发给 AI："请解释为什么相同密码加盐后哈希不同？数据库泄露时加盐能保护什么？"一句话记录理解。

13.2.4 了解：正则进阶——分组、修饰符与贪婪

13.2.2 只用了 findall 提取。真实场景还常用三样：分组（把匹配结果拆成几块）、修饰符（改变匹配规则）、贪婪/非贪婪（控制匹配长度）。

代码案例 13.6：分组提取（✅ 正确，实测过）

python
import re

text = "今天是2025-08-01 明天是2025-08-02"
pattern = r"(\d{4})-(\d{2})-(\d{2})"

for match in re.finditer(pattern, text):
    print(f"完整：{match.group()}，年：{match.group(1)}，月：{match.group(2)}，日：{match.group(3)}")

运行结果：

完整：2025-08-01，年：2025，月：08，日：01
完整：2025-08-02，年：2025，月：08，日：02

讲解：() 括起来的部分成为分组；finditer 逐个返回匹配对象，group() 完整匹配、group(1) 第一个分组……分组让"提取"变成"结构化提取"。

代码案例 13.7：修饰符与贪婪/非贪婪（✅ 正确，实测过）

python
import re

# re.I：忽略大小写
print(re.findall(r"python", "Python PYTHON python", re.I))

# 贪婪 vs 非贪婪
html = "<a>1</a><a>2</a>"
print(re.findall(r"<a>(.*)</a>", html))    # 贪婪：尽量多匹配
print(re.findall(r"<a>(.*?)</a>", html))   # 非贪婪：尽量少匹配

运行结果：

['Python', 'PYTHON', 'python']
['1</a><a>2']
['1', '2']

讲解：

  • re.I 让匹配忽略大小写（还有 re.M 多行、re.S 让 . 匹配换行，了解即可）；
  • .* 贪婪：尽量匹配到最远（一次吞掉 1</a><a>2）；.*? 非贪婪：匹配到最近就停（分别得到 1 和 2）；
  • 解析 HTML 时贪婪匹配是经典 bug 源——这正是"不要用正则解析 HTML、用解析器（第 26 章 BeautifulSoup）"的原因之一。

就业红线（了解级边界）：正则这里只是进阶了解；数据清洗/爬虫/后端岗位要求能写常见模式（邮箱、URL、日期），并会用分组提取。面试问"贪婪与懒惰匹配"，答".* 尽量多、.*? 尽量少"即可。

04. 13.3 并发：线程与 GIL ▼

13.3.1 概念认知：顺序、并发、并行

程序执行任务的方式有三种：

  • 顺序：一件做完再做下一件；
  • 并发（concurrency）：多个任务交替进行（宏观上同时，微观上轮流）；
  • 并行（parallelism）：多个任务真正同时执行（多核 CPU）。

代码案例 13.8：顺序执行两个耗时任务（✅ 对比基准）

python
import time

def work(name, seconds):
    time.sleep(seconds)
    print(f"{name} 完成")

start = time.time()
work("任务A", 0.2)
work("任务B", 0.2)
print(f"顺序总耗时：{time.time() - start:.2f} 秒")

运行结果：

任务A 完成
任务B 完成
顺序总耗时：0.40 秒

13.3.2 语法掌握：threading 线程

代码案例 13.9：两个线程并发执行（✅ 正确）

python
import threading
import time

def work(name, seconds):
    time.sleep(seconds)
    print(f"{name} 完成")

start = time.time()

t1 = threading.Thread(target=work, args=("任务A", 0.2))
t2 = threading.Thread(target=work, args=("任务B", 0.2))

t1.start()
t2.start()

t1.join()      # 等 t1 结束
t2.join()      # 等 t2 结束

print(f"并发总耗时：{time.time() - start:.2f} 秒")

运行结果：

任务A 完成
任务B 完成
并发总耗时：0.20 秒

讲解：

  • threading.Thread(target=函数, args=(参数,)) 创建线程；start() 启动；join() 等待结束；
  • 两个 0.2 秒的任务并行等待，总耗时约 0.2 秒（顺序要 0.4 秒）——耗时减半；
  • 注意：print 的输出顺序可能变（A/B 谁先完成不保证），这是并发的基本特征。

13.3.3 原理探秘：GIL 一句话说清

GIL（全局解释器锁）：CPython 规定同一时刻只有一个线程能执行 Python 字节码。

为什么？CPython 的内存管理（引用计数）不是线程安全的，加锁最简单可靠。

影响：多线程对"计算密集"任务没有加速（都在抢同一把锁）；但对"等待密集"（网络、磁盘、睡眠）任务有用——因为等待时线程会释放 GIL，让其他线程跑。

对策：

  • IO 密集（请求、读写）→ 多线程 / asyncio；
  • CPU 密集（大量计算）→ 多进程（multiprocessing，每进程一个解释器）或 C 扩展。

面试标准答法："GIL 是 CPython 的全局解释器锁，同一时刻只允许一个线程执行字节码；它限制的是 CPU 密集型的并行，不影响 IO 密集型的并发。"——背下来，这是 Python 面试最高频的问题之一。

13.3.4 语法掌握：多进程——CPU 密集的正确姿势

GIL 让多线程对"纯计算"无效，但 multiprocessing 给每个进程一个独立解释器——每个进程都有自己的 GIL，多个 CPU 核可以真正同时算。

代码案例 13.10：ProcessPoolExecutor（✅ 正确，实测过）

python
from concurrent.futures import ProcessPoolExecutor

def cpu_heavy(n):
    """模拟 CPU 密集：计算 1 到 n 的平方和"""
    total = 0
    for i in range(1, n + 1):
        total += i * i
    return total

if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=4) as pool:
        results = list(pool.map(cpu_heavy, [1000000] * 4))
    print(results)

运行结果（4 个进程各算一份，结果相同）：

[333333833333500000, 333333833333500000, 333333833333500000, 333333833333500000]

讲解：

  • ProcessPoolExecutor：进程池——把任务分给多个进程并行执行；
  • if __name__ == "__main__": 在 Windows 上必须写：多进程用"导入方式"启动子进程，没有主进程保护会无限递归启动；
  • 每个子进程独立内存（不共享变量），结果通过返回值传回——和线程共享内存的模型完全不同。

交叉验证：线程/进程/协程选型表

多线程 threadingIO 密集、任务少共享内存方便，但受 GIL 限制

协程 asyncioIO 密集、任务多最轻量、可开上万个，但要求异步写法

口诀：CPU 密集用多进程，IO 密集任务少用线程、任务多用协程。

05. 13.4 异步：asyncio 协程 ▼

13.4.1 概念认知：协程 vs 线程

线程由操作系统调度，切换有开销；协程（coroutine）由程序自己调度——遇到等待（await）就主动让出控制权，让别的任务先跑。asyncio 就是 Python 的协程框架。

13.4.2 语法掌握：async / await 基础

代码案例 13.11：第一个协程（✅ 正确）

python
import asyncio

async def hello():
    print("开始")
    await asyncio.sleep(0.1)
    print("结束")

asyncio.run(hello())

运行结果：

开始
结束

讲解：

  • async def 定义协程函数；调用它不执行，而是返回协程对象；
  • await asyncio.sleep(0.1)：遇到等待就"挂起"，把控制权交回事件循环；
  • asyncio.run(协程)：启动事件循环并运行协程（入口函数）。

13.4.3 语法掌握：gather 并发执行

代码案例 13.12：并发执行多个协程（✅ 正确）

python
import asyncio
import time

async def task(name, seconds):
    await asyncio.sleep(seconds)
    return f"{name} 完成"

async def main():
    start = time.time()
    results = await asyncio.gather(
        task("任务A", 0.2),
        task("任务B", 0.2),
    )
    print(results)
    print(f"异步总耗时：{time.time() - start:.2f} 秒")

asyncio.run(main())

运行结果：

['任务A 完成', '任务B 完成']
异步总耗时：0.20 秒

讲解：

  • asyncio.gather(协程1, 协程2) 把多个协程并发调度，一起等待完成；
  • 两个 0.2 秒任务总耗时约 0.2 秒——和 threading 效果类似，但没有线程切换开销，能开的任务数量大得多（轻松上万）；
  • 真实场景：同时请求多个 API、同时下载多个文件、Web 服务处理大量并发连接。

13.4.4 原理探秘：事件循环

asyncio 的核心是事件循环（event loop）：

事件循环：
1. 取出一个就绪任务 → 执行到 await（等待点）
2. 挂起它，换下一个就绪任务
3. 等待完成的事件回来了 → 继续执行对应协程

关键认识：异步不是"更快"，而是不浪费等待时间——任务在等待网络/磁盘时，CPU 去干别的活了。选型口诀：

场景方案
IO 密集（网络请求、读写文件）asyncio 协程（首选）或 threading
CPU 密集（大量计算）multiprocessing 多进程
简单脚本顺序执行就够

13.4.5 就业实战：并发请求、超时与同步库适配

学完基础，看三个真实后端场景的写法。

场景一：并发请求多个接口（httpx 异步客户端）

代码案例 13.13：AsyncClient + gather（✅ 正确，实测过）

python
import asyncio
import httpx          # 需要 pip install httpx

async def fetch(client, i):
    resp = await client.get(f"https://api.example.com/data/{i}")
    return resp.json()

async def main():
    async with httpx.AsyncClient(timeout=10) as client:
        results = await asyncio.gather(
            *[fetch(client, i) for i in range(5)]
        )
    print(results)

asyncio.run(main())

讲解：

  • httpx.AsyncClient 是支持异步的 HTTP 客户端（requests 是同步的，在协程里会阻塞事件循环）；
  • async with 管理客户端连接池（自动关闭）；
  • gather 并发发起 5 个请求——总耗时取决于服务器能否并行处理，但客户端绝不串行等待；
  • 就业提示：后端接口并发调多个上游服务时，这就是标准写法。

场景二：控制超时（wait_for）

代码案例 13.14：防止接口卡死（✅ 正确，实测过）

python
async def slow_request():
    await asyncio.sleep(2)
    return "完成"

async def main():
    try:
        await asyncio.wait_for(slow_request(), timeout=5)
    except asyncio.TimeoutError:
        print("请求超时，已取消")

讲解：真实网络随时可能卡住——wait_for(协程, timeout) 超时后自动取消任务，是"请求必须有超时"（13.6 节 Debug 问题 2）的异步版。

场景三：适配同步库（to_thread）

代码案例 13.15：把 requests 丢进线程池（✅ 正确，实测过）

python
async def main():
    results = await asyncio.gather(
        asyncio.to_thread(requests.get, "https://api.example.com/a"),
        asyncio.to_thread(requests.get, "https://api.example.com/b"),
    )
    print([r.status_code for r in results])

讲解：没有异步版的库（如 requests）不能直接 await——asyncio.to_thread(函数, 参数) 把它放到线程池里执行，事件循环不被阻塞。这是"老库 + 新异步"的桥梁。

就业提示：三个场景合起来就是"生产级并发接口"的骨架：AsyncClient 并发 + wait_for 超时 + to_thread 兼容旧库。后端面试问"异步怎么落地"，能说出这三个就是实战经验。

第 7 题：线程共享计数器"受控竞争"实验。创建 8 个线程，每个线程把全局变量 count 累加 500 次，但必须手动写"读-改-写"三步：先 tmp = count，再 time.sleep(0)（主动让出 CPU，制造线程切换机会，模拟真实场景中线程被随时切换），最后 count = tmp + 1。运行 3 次，观察 count 是否每次都等于 4000，并在注释中解释原因。再用 ProcessPoolExecutor 重新实现（每个进程在局部变量上累加 500 次并返回结果，主进程求和），验证结果为 4000，并对比"线程共享内存"与"进程独立内存"两种方案的差异。

📝 参考答案

第 1 部分参考答案（受控竞争）：

python
import threading
import time

count = 0

def add():
    global count
    for _ in range(500):
        tmp = count        # ① 读
        time.sleep(0)      # ② 主动让出 CPU，制造线程切换
        count = tmp + 1    # ③ 写回

for run in range(3):
    count = 0
    threads = [threading.Thread(target=add) for _ in range(8)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    print(f"第 {run + 1} 次运行：count = {count}（预期 4000）")

运行结果（每次运行的数值不固定）：

第 1 次运行：count = 2093（预期 4000）
第 2 次运行：count = 784（预期 4000）
第 3 次运行：count = 707（预期 4000）
🔍 解析

count = tmp + 1 看起来是一行，实际是"读-改-写"三步：先读旧值，再计算，最后写回。time.sleep(0) 让线程在"读完之后、写回之前"被切换走，其他线程也完成了一次"读-改-写"——等原线程回来写回时，覆盖了别人刚写好的值，这就是"丢失更新"（race condition）。

关键认知：GIL 只保证"同一时刻只有一个线程执行字节码"，不保证这三步作为一个整体不被切换。所以 GIL 解决不了共享数据竞争，凡是被多个线程修改的共享变量都必须额外保护。

第 2 部分参考答案（进程隔离修复）：

python
from concurrent.futures import ProcessPoolExecutor

def add_local(times):
    local = 0
    for _ in range(times):
        local += 1
    return local

if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=8) as pool:
        results = list(pool.map(add_local, [500] * 8))
    print(f"进程池求和结果：{sum(results)}（预期 4000）")

运行结果：

进程池求和结果：4000（预期 4000）

解析：每个进程都有独立内存，各自在局部变量 local 上累加 500 次，不存在共享变量，最后通过返回值在主进程汇总——从根源上避免竞争。对比结论：线程共享内存（方便但危险，需要锁等保护），进程独立内存（安全，但通信成本高）。本题没有要求写 threading.Lock（了解即可，第 14 章综合训练可自行探索）：加锁的本质就是让"读-改-写"三步变成原子操作。

参考答案：

python
import asyncio
import time
import httpx
import requests

async def fetch(client, i):
    resp = await client.get(f"https://httpbin.org/get?id={i}")
    return resp.json()["args"]["id"]

async def slow_request():
    await asyncio.sleep(3)      # 模拟一个 3 秒才返回的慢接口
    return "慢接口数据"

def sync_fetch():
    resp = requests.get("https://httpbin.org/get?source=sync")
    return resp.json()["args"]["source"]

async def main():
    start = time.time()

    # 场景一：AsyncClient 并发
    async with httpx.AsyncClient(timeout=10) as client:
        results = await asyncio.gather(*[fetch(client, i) for i in range(3)])
    print("并发结果：", results)

    # 场景二：wait_for 超时控制
    try:
        await asyncio.wait_for(slow_request(), timeout=1)
    except asyncio.TimeoutError:
        print("慢接口超时，已取消")

    # 场景三：to_thread 适配同步库
    sync_result = await asyncio.to_thread(sync_fetch)
    print("同步库适配结果：", sync_result)
    print(f"总耗时：{time.time() - start:.2f} 秒")

asyncio.run(main())

运行结果（网络耗时不同，数值会有波动）：

并发结果： ['0', '1', '2']
慢接口超时，已取消
同步库适配结果： sync
总耗时：3.47 秒
🔍 解析
  • AsyncClient + gather：3 个请求并发发出，不串行等待；
  • wait_for(慢协程, timeout=1)：慢接口本来要 3 秒，1 秒后就被取消并抛出 asyncio.TimeoutError——"请求必须有超时"在生产环境是硬要求，防止接口卡死拖垮整个服务；
  • to_thread(requests.get, ...)：requests 是同步库，放进线程池后事件循环不会被阻塞；
  • 结论：异步的价值不是"快"，而是"不让任何一段等待拖住整个程序"。日志第 4 题要写的就是：wait_for 负责"砍掉超时等待"，to_thread 负责"兼容没有异步版的旧库"。

09. 13.8 本章小结与知识树 ▼

知识树：

第三方库、并发与异步
├── 第三方库：pip install → import；PyPI 生态；ModuleNotFoundError 排查
├── requests
│   ├── GET：resp.status_code / resp.text / resp.json()
│   ├── POST：json= 自动序列化
│   ├── HTTP 四要素：方法/URL/头/体；响应三要素：状态码/头/体
│   └── 失败：ConnectionError → try/except + @retry
├── datetime：日期相减 → timedelta.days；生日天数/到期计算
├── re：findall(模式, 文本)；\d 数字、{9} 次数、[3-9] 范围
├── 并发
│   ├── 顺序 vs 并发 vs 并行
│   ├── threading：Thread(target, args) / start() / join()
│   ├── GIL：同一时刻一个线程执行字节码；IO 密集有用、CPU 密集没用
│   └── multiprocessing：ProcessPoolExecutor（CPU 密集真并行，Windows 要主进程保护）
├── asyncio
│   ├── async def / await / asyncio.run / gather
│   ├── 事件循环：遇到 await 挂起，等待时不浪费 CPU
│   ├── 就业实战：httpx.AsyncClient 并发 / wait_for 超时 / to_thread 适配同步库
│   └── 坑：协程里用 time.sleep 会阻塞事件循环
└── 选型：IO 密集任务多 → asyncio；IO 密集任务少 → 线程；CPU 密集 → 多进程；简单脚本 → 顺序

必须记住的 5 件事：

  1. 第三方库先 pip install 再 import，环境要对应；
  2. resp.json() 只对 JSON 内容有效；网络请求必须 try/except；
  3. GIL：同一时刻一个线程执行字节码——IO 密集用线程/协程，CPU 密集用多进程；
  4. 异步代码里用 await asyncio.sleep()，不要用 time.sleep；
  5. 生产级异步三件套：AsyncClient 并发 + wait_for 超时 + to_thread 适配旧库；
  6. 并发不是"更快"，而是"等待时不空闲"——这就是异步的核心价值。
