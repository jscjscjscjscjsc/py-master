02. Day 38｜前端展示与容器化 ▼

一、教学目标

  1. 用 Gradio / Streamlit 给应用加一个能用的界面（含流式打字机效果）；
  2. 会用 Docker 打包应用，做到「换个环境也能跑」；
  3. 知道容器化的常见坑。

二、为什么需要前端

给非技术用户用的产品必须有界面。 命令行输出对演示够用，对产品是不够的。而 LLM 应用的界面有一个特殊要求：

流式输出（打字机效果）不是装饰，是体验必需品。

等待全部生成完再显示逐字流式显示
首字可见时间5–15 秒（等于总生成时间）0.3–1 秒
用户感知「卡住了？是不是坏了？」「它在打字，在工作」
心理等待时长等于实际时长显著短于实际时长

这是真实的产品指标，不是审美偏好。同一次响应，流式能让用户的主观等待感下降一半以上。 所以第 2 章 Day08 花大力气讲 SSE，就是为了这一天。

三、Gradio 与 Streamlit

GradioStreamlit
定位快速搭建 ML/AI 演示界面数据应用与仪表盘
对话界面gr.ChatInterface 开箱即用需要自己组合
流式支持回调函数 yield 部分结果st.write_stream(generator)
适合本课程：聊天类应用带图表的分析面板
部署可挂 Hugging Face Spaces需要自己部署

共同的优点：几行代码就有可用界面，把时间留给业务逻辑。

Gradio 的流式写法（要点）

python
import gradio as gr

def respond(message, history):
    # 关键：用 yield 逐步返回，而不是 return 一次性返回
    buffer = ""
    for piece in client.stream([...]):
        buffer += piece
        yield buffer          # 每次 yield 都会更新界面

gr.ChatInterface(fn=respond).launch()

⚠️ 两个高频误区（已核实，核实日期 2026-09-21，Gradio 当前 6.28.0）：

  1. 打字机效果不是靠 .stream() 实现的。.stream() 是输入组件的事件
  2. Gradio 6 有几个破坏性变更（都是实测踩出来的）：
    • gr.Chatbot(type=...) 参数已被移除，传了会直接 TypeError（messages 格式现为默认）；
    • theme 参数从 Blocks() 移到了 launch()；
    • ChatInterface 的 type 参数同样不存在了。

一个必须搞清的语义差异（这是实测发现的，很多教程讲错）：

框架生成器 yield 的应该是
Gradio累积的完整文本（每次 yield 完整内容，它内部算 diff 只发增量）
Streamlit增量分片（st.write_stream 自己负责拼接）

两者方向相反。如果你在两个框架间复用同一个生成器函数，必须写一个适配函数转换语义， 否则 Gradio 上会看到文字重复叠加、Streamlit 上会看到只有最后一片。

官方 demo 的写法就是最标准的：

python
def slow_echo(message, history):
    for i in range(len(message)):
        time.sleep(0.05)
        yield "You typed: " + message[: i + 1]     # ← 注意是累积的完整字符串

Streamlit 的流式写法（要点）

python
import streamlit as st

def stream_data():
    for piece in client.stream([...]):
        yield piece

if prompt := st.chat_input("问点什么"):
    st.write_stream(stream_data)      # 自动渲染打字机效果

已核实：st.write_stream(stream, *, cursor=None) 当前版本 v1.64.0。 它"iterates through the given sequences and writes all chunks to the app"， 字符串分片用 typewriter effect 显示，并返回完整响应。 cursor 参数（1.51.0 加入）可自定义光标；1.59.0 起还支持 OpenAI Responses API 的流。 它同样支持 async generator（1.41.0 起）。

两者的共同本质：把一个生成器交给界面框架，它负责在每次产出时刷新视图。 理解这一点，你就能在任意前端框架里实现同样的效果。

四、容器化：让「换个环境也能跑」成为默认

为什么必须容器化

「在我机器上能跑」是工程事故的头号来源。 它通常来自：

差异容器如何解决
Python 版本不同镜像固定版本
依赖版本不同requirements.txt 锁定 + 镜像固化
系统库缺失Dockerfile 里显式安装
环境变量不同用 .env 或 compose 显式声明
工作目录结构不同镜像内路径固定

Dockerfile 的关键要素

dockerfile
# 1. 基础镜像固定版本（不要用 latest —— 那等于每天换一次环境）
FROM python:3.12-slim

# 2. 先复制依赖清单再装依赖（利用 Docker 层缓存：
#    只要 requirements.txt 没变，改代码时不会重装依赖）
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 3. 再复制代码（这一步频繁变化，放在后面）
COPY code/ ./code/
COPY tools/ ./tools/

# 4. 用非 root 用户运行（安全要求，不要用 root 跑应用）
RUN useradd -m appuser
USER appuser

# 5. 健康检查（编排系统靠它判断容器是否真的可用）
HEALTHCHECK CMD python -c "import httpx; httpx.get('http://127.0.0.1:8000/health').raise_for_status()"

EXPOSE 8000
CMD ["uvicorn", "code.ch02.api:app", "--host", "0.0.0.0", "--port", "8000"]

基础镜像的当前情况（核实日期 2026-09-21）：

  • python:3.12-slim 依然有效可用，是社区主流写法。官方 tag 清单确认存在
  • 当前最新稳定线是 3.14（另有 3.15 RC），若想用最新可写 python:3.14-slim；
  • 但要注意：Docker 官方 Python 指南现在已改用 Docker Hardened Images (DHI)

教学建议：课堂用 python:3.12-slim（开放、易拉取、写法通用）。 但在讲义和答辩里不要声称「这是 Docker 官方推荐」—— 官方当前推荐的是 DHI，只是它需要账号，不适合课堂。

每一行的理由：

做法为什么
固定基础镜像版本latest 会在某天悄悄换版本，导致「昨天还好好的今天崩了」
依赖先复制层缓存：改代码不触发依赖重装，构建从几分钟降到几秒
--no-cache-dirpip 缓存会白白增大镜像体积
非 root 用户容器逃逸时限制影响范围
HEALTHCHECK编排系统据此重启不健康的容器
不要复制 .env密钥必须通过运行时注入，不能进镜像（镜像层可被任何人拉取查看）

常见坑（.dockerignore 的必要性）

坑后果解决
把 .env 打进了镜像密钥泄露.dockerignore 排除 .env，改用运行时注入
把 .git / venv / __pycache__ 打进去镜像从 200MB 变成 2GB.dockerignore
用 root 运行安全风险USER 指令
没有健康检查编排系统无法判断容器状态HEALTHCHECK
每次改代码都重装依赖构建慢依赖与代码分层复制

03. Day 39｜LLMOps：监控、成本与安全上线 ▼

一、教学目标

  1. 建立 LLM 应用的四个监控维度；
  2. 用真实数据做成本核算与预警；
  3. 完成上线前的安全检查清单。

二、LLM 应用要监控什么

传统后端监控 CPU、内存、QPS。LLM 应用需要额外监控四类指标：

维度指标为什么 LLM 应用特别需要
质量拒答率、格式遵循率、引用正确率、用户反馈模型输出没有"异常栈"，质量退化是静默的
成本token 消耗、单次成本、按用户/功能拆分成本随上下文长度动态变化，且可能在无人察觉时翻倍
性能首字延迟（TTFT）、总延迟 P50/P95、流式速率首字延迟是流式体验的核心指标，与总延迟是两回事
可靠性上游错误率、重试次数、限流触发次数上游模型服务会波动，必须有降级方案

最容易被忽略的两个指标

指标一：首字延迟（TTFT, Time To First Token）

流式场景下，用户感知的是 TTFT，不是总延迟。一个 10 秒生成、TTFT 0.5 秒的响应， 体验远好于 5 秒生成、TTFT 4 秒的响应。优化要优化对的那个。

指标二：拒答率

拒答率双向都危险：

  • 太高 → 用户在正常问题上被拒，体验崩坏；
  • 太低 → 说明护栏没生效，模型在编造（第 3 章的拒答阈值就是管这个的）。

必须同时监控两个方向，只看一头会走向另一个极端。

三、成本监控与预警

powershell
python code/ch09/30_llmops_dashboard.py

脚本会：

  1. 从历史运行记录中统计每日调用量、token 消耗、成本、失败率、P50/P95 延迟；
  2. 画趋势图（便于发现异常拐点）；
  3. 执行成本预警逻辑。

!LLMOps 监控面板

!LLMOps 成本与质量趋势

读图的三个要点：

  1. 看趋势而不是看绝对值：某天成本高可能是正常的业务高峰，
  2. 把 P95 和成本放在一起看：延迟上升往往伴随 token 增加（上下文变长），
  3. 失败率要看状态码分布，不只看总数 —— 429（限流）和 5xx（上游故障）

成本预警的三条规则（实践经验）

规则目的
日总量告警：日成本超过预算线防止异常流量或死循环
单请求告警：单次请求 token 超过阈值发现上下文失控（通常是历史没清理）
趋势告警：同期成本环比上涨超过 X%发现缓慢的劣化（如用户开始问更长的问题、知识库变大）

第三条最容易忽视，也最有价值：突然翻倍的问题容易被发现， 每周涨 10% 的缓慢劣化往往三个月后才被察觉，那时成本已经翻了三倍。

四、上线前的安全检查清单

检查项怎么验证
密钥不在代码里全局搜索 sk- / 密钥模式，确认无硬编码
密钥不在镜像里检查 .dockerignore，构建后 env 检查
密钥不在日志里检查日志输出是否打印了 Authorization
密钥不在 Git 历史里`git log -p \grep -i "api_key"`；如果提交过，必须轮换密钥（删历史也不够，因为可能已被克隆）
用户输入做了长度限制构造超长输入测试
文件上传有类型与大小限制上传超大文件与非法扩展名测试（第 2 章 Day09）
写操作需要人工确认测试高危工具（删除/支付/发送）是否必须确认
有速率限制连续快速请求，验证限流生效
错误响应不泄露内部信息触发上游错误，检查返回给客户端的内容
有成本上限构造超长对话，验证预算护栏生效
有降级方案断开上游，验证是否有友好的错误提示而不是白屏
提示词注入有防护用第 1 章 Day04 的注入测试集跑一遍

密钥泄露的第一处置不是删代码，是轮换密钥。 因为密钥一旦进入 Git 历史或被推到公开仓库，就必须假设它已经泄露。 删掉历史只能防止后续泄露，不能收回已泄露的密钥。

04. Day 40｜毕业答辩与就业指导 ▼

一、答辩要求

15 分钟演示 + 10 分钟提问。

演示结构（建议时间分配）

时间内容要点
2 min问题与价值解决什么问题？给谁用？不讲技术
3 min现场演示真跑，不播录像。包含一次成功路径 + 一次失败路径
5 min技术架构分层图 + 为什么这样分层 + 一个关键取舍
3 min数据与证据评测数据、成本数据、性能数据（有数字才有说服力）
2 min边界与演进现在不能做什么？下一步做什么？

评分重点

维度关键看什么
完整性前端 → 后端 → 数据 → 部署，链路是否完整
工程质量配置外置、异常处理、测试、文档
数据意识有没有评测数据？改动有没有量化对比？
深度能不能讲清一个子系统的设计取舍（而不只是"我用了 X 框架"）
诚实能否清楚说出系统的局限与不足
表达听众（非本方向的人）能否听懂核心价值

「诚实」单独列为评分项：答辩时说「这里我用了一个不太好的方案， 因为时间限制，如果重做我会改成 X」比硬说「我的方案很完美」得分高得多。 面试官和评委都见过大量项目，能指出自己方案局限的人，才是真的理解了问题。

二、高频答辩问题（按类型准备）

架构类

  1. 画出你的系统架构图，说明每一层的职责与依赖方向。
  2. 如果要支持 1 万并发用户，哪里会先扛不住？怎么改？
  3. 为什么用（不用）框架？这个取舍的依据是什么？

数据与评测类

  1. 你怎么证明你的改动是有效的？给出具体的对比数据。
  2. 你的评测集是怎么设计的？覆盖了哪些边界情况？
  3. 有没有哪个指标看起来变好但实际体验变差的情况？

成本与性能类

  1. 一次请求的成本是多少？怎么算出来的？
  2. P95 延迟是多少？瓶颈在哪一层？
  3. 如果成本要降一半，你会先动哪里？

安全与可靠性类

  1. 如何防止提示词注入？你的防护在哪几层？
  2. 上游模型服务挂了，你的系统怎么表现？
  3. 密钥是怎么管理的？如果泄露怎么办？
  4. 写操作（删除/支付）如何防止误执行？

反思类

  1. 这个项目里你最不满意的部分是什么？为什么当时那样做了？
  2. 如果给你两周时间继续做，你的优先级是什么？

准备方法：不是背答案，而是每个问题都准备一个具体的例子或数字。 「我们做了限流」不如「我们用了滑动窗口限流，单用户每秒 5 次， 压测时 20 并发触发了限流，成功率从 100% 降到 92%」——后者才叫回答了问题。

三、作品集（GitHub 仓库）规范

README 必须有的七块（这是招聘方真正会看的）：

markdown
# 项目名 — 一句话说明它做什么

## 1. 演示（截图 / GIF，30 秒内看懂）
## 2. 快速开始（3 条命令能跑起来，用离线靶场，不需要密钥）
## 3. 架构图（分层 + 数据流）
## 4. 关键设计决策（2-3 个取舍，说明为什么）
## 5. 评测数据（有对比表，不是"效果良好"）
## 6. 成本与性能（真实数字）
## 7. 已知局限与后续计划

第 2 条和第 7 条最容易加分，也最容易被忽略：

  • 第 2 条：如果招聘方需要花 30 分钟配环境才能跑起来，他大概率会关掉页面。
  • 第 7 条：主动写出局限，显得可信。

四、简历中的 AI 应用岗（怎么写才不像培训班作业）

❌ 常见写法✅ 更好的写法

05. 9.10 全课程回顾 ▼

40 天，你走过了这条路径：

章你获得的可迁移能力（不是知识点）
1会测量：把「感觉更好」变成「通过率 +42%，成本 +76%」
2会交付服务：把脚本变成别人能调用的接口
3会控制知识来源：让模型基于证据说话，且能溯源
4会让模型动手：工具调用、循环控制、安全边界
5会编排：用状态图管理复杂流程与人工介入
6会协作与标准化：多 Agent、开放协议、可观测、成本护栏
7会读与抽象：从开源项目里提取设计，并自己造框架
8会理解模型内部：知道微调与 RAG / Prompt 的边界
9会交付产品：界面、容器、监控、安全、答辩

最后一条建议：技术会变。这 40 天里你用的具体模型 ID、框架版本、协议版本， 一年后可能都变了。但你建立的这些习惯不会变：

  • 用数据而不是感觉做判断；
  • 用评测集守住改动质量的底线；
  • 用配置化隔离变化；
  • 用分层隔离复杂度；
  • 用诚实对待系统的边界。

这些才是这 40 天真正的产出。
