02. 21.1 架构是什么 ▼

21.1.1 概念认知：架构 = 系统的骨架

第 16 章的分层思想是"一个程序的内部组织"；架构（architecture） 是"整个系统的组织"：系统分哪些部分、每部分干什么、部分之间怎么通信。

类比：盖楼先有蓝图（架构），再砌砖（编码）。没有蓝图的楼能盖起来，但加不了层、改不了水电、塌了不知道哪根梁的问题。

好架构的标志：

  1. 各部分职责清晰（谁管界面、谁管业务、谁管数据）；
  2. 改动局部化（换数据库不动界面，改界面不动业务）；
  3. 可扩展（加新功能不用推翻重来）。

21.1.2 语法掌握：三层架构

最经典的架构是三层架构：

表现层（Presentation）    界面：菜单、网页、App 页面
   │ 调用
   ▼
业务逻辑层（Business）    规则：统计、校验、判断
   │ 调用
   ▼
数据访问层（Data）        存取：文件、数据库、API

代码案例 21.1：三层架构在 Python 中的对应（✅ 你 Day 9 已经写过）

python
# 数据层：只管读写
def load_students(path):
    with open(path, "r", encoding="utf-8") as f:
        return json.load(f)

# 逻辑层：只管业务规则
def calc_stats(scores):
    if not scores:
        return None
    ...

# 表现层：只管输入输出
def main():
    data = load_students("students.json")
    ...

交叉验证：分层的好处用一个场景验证

场景：要把数据从 JSON 文件换成 SQLite 数据库（第 23 章）。

❌ 不分层：改文件代码时，统计逻辑、打印逻辑全要跟着动——牵一发动全身； ✅ 分层：只改数据层（load_students 内部实现），逻辑层和表现层一行不用动。

讲解：分层的目的就是"隔离变化"——让每一类变化只影响它该影响的层。这是第 16 章"高内聚低耦合"在系统级别的大号版本。

03. 21.2 MVC 模式 ▼

21.2.1 概念认知：MVC 是什么

MVC 是 Web 开发最经典的架构模式，把程序拆成三部分：

Model（模型）    数据和业务规则（相当于业务逻辑层 + 数据层）
View（视图）     用户看到的界面（相当于表现层）
Controller（控制器） 接收用户操作，调度 Model 和 View

一次典型请求的流程：

用户在浏览器点"提交"
  → Controller 收到请求
  → 调用 Model 处理数据（校验、存库）
  → 选择 View 渲染结果
  → 浏览器显示新页面

代码案例 21.2：MVC 的 Python 对应（✅ 概念示例）

python
# Model：数据 + 规则
class Student:
    def __init__(self, name, score):
        self.name = name
        self.score = score

# View：界面渲染（这里用字符串模拟网页）
def render_student(student):
    return f"<p>{student.name}: {student.score}</p>"

# Controller：接收操作、调度 Model 和 View
def handle_submit(name, score):
    student = Student(name, score)      # 调 Model
    return render_student(student)      # 选 View

21.2.2 了解：Django 的 MVT

Python 的 Django 框架用 MVT（Model-View-Template）：Model 管数据、View 管业务逻辑、Template 管页面。和 MVC 本质相同（名字不同），第 26 章了解 Django 时会再看到。

了解级边界（就业提示）：MVT 了解即可；Django 岗位要求会用 Model/View/Template 实际开发（ORM 查询、模板渲染、URL 路由）。面试答"MVT 与 MVC 的区别"——"名字不同、思想相同，Django 的 View 承担 Controller 的角色"。

04. 21.3 单体 vs 前后端分离 ▼

21.3.1 概念认知：两种架构形态

单体架构：前端页面 + 后端逻辑 + 数据库都在一个应用里，一起部署。

前后端分离：

浏览器（前端：HTML/CSS/JS 或 Vue）
   │ HTTP 请求（JSON）
   ▼
后端（FastAPI 等，提供 API）
   │
   ▼
数据库

对比：

维度单体前后端分离
部署一个应用一起部署前端、后端各自独立部署
通信页面直接渲染前端调 API（JSON）
团队全栈一人/一组搞定前端组 + 后端组分工
适合小工具、内部系统Web/App 产品、大团队
本课程项目——最终项目采用（Vue + FastAPI）

21.3.2 原理探秘：为什么现在流行前后端分离

  1. 分工：前端工程师和后端工程师可以并行开发，互不阻塞；
  2. 复用：后端 API 一套，网页、手机 App、小程序都能用（"一次开发，多端消费"）；
  3. 演进：后端升级不影响前端（接口稳定即可），前端框架换代不影响后端；
  4. 职责清晰：各管各的，出问题好定位。

代价：多了一层"接口约定"（API 文档），前后端必须对齐数据结构——这正是第 23 章 REST API 的意义。

06. 21.5 本章 Debug 四件套（架构类） ▼

问题 1：没有架构的"大泥球"

问题描述：程序所有代码堆在一个文件里，加功能越来越难，改一行不知道影响哪里。

提示：第 16 章哪条原则能救你？

讲解：分层 + 模块化。先按"数据/逻辑/界面"拆开，再逐步细化——大泥球不是一天形成的，拆也不是一次完成的。

问题 2：层与层"串层"

问题描述：界面代码里直接写了 SQL，业务逻辑里直接 print。

提示：每层该干什么？串了会怎样？

讲解：表现层不碰数据、数据层不碰界面。串层 = 改动互相传染。发现"界面里出现数据库语句"就是坏味道。

问题 3：前后端"接口漂移"

问题描述：后端把返回字段从 name 改成 full_name，前端还在用 name——页面空白。

提示：前后端之间靠什么约束？

讲解：API 文档（接口契约）。任何一方改接口，必须同步更新文档并通知对方——第 23 章 REST 设计就是建立这份契约。

问题 4：为了"架构"而架构

问题描述：10 行代码的工具，非要拆成 5 个文件、3 个设计模式。

提示：架构是服务于什么的？

讲解：架构的复杂度必须匹配项目的复杂度。小工具就一个文件，系统才分层——"合适的架构"才是好架构（YAGNI：不要过度设计）。

08. 21.7 本章小结与知识树 ▼

知识树：

软件架构基础
├── 架构 = 系统骨架：职责清晰 / 改动局部化 / 可扩展
├── 三层架构：表现层 / 业务逻辑层 / 数据访问层（隔离变化）
├── MVC：Model（数据规则）/ View（界面）/ Controller（调度）
│   └── Django 的 MVT 是同一思想
├── 单体 vs 前后端分离
│   ├── 单体：一起部署，适合小项目
│   └── 分离：前端调 API（JSON），分工/复用/演进，本课程项目采用
├── 架构图：文字层级 / ASCII 框图 / 专业工具
└── 原则：架构复杂度匹配项目复杂度（YAGNI）

必须记住的 5 件事：

  1. 架构 = 职责清晰 + 改动局部化 + 可扩展；
  2. 三层：表现层不碰数据、数据层不碰界面；
  3. MVC = Model / View / Controller，Web 开发经典模式；
  4. 前后端分离的核心是"接口契约"（API 文档）；
  5. 小项目别过度设计——合适的架构才是好架构。
