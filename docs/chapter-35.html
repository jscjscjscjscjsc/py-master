03. 35.3 任务一：演示准备 ▼

35.3.1 演示数据（提前备好）

3-5 篇有内容的笔记，建议覆盖：一篇带代码块（展示高亮）、一篇长文（展示摘要）、两篇同主题（展示问答引用）。禁止现场现写长笔记——演示时间只花在"展示"，不花在"等待输入"。

35.3.2 8 分钟演示脚本

时间环节内容
30 秒价值"AI 学习笔记助手：边写笔记，边让 AI 帮我整理和问答，引用可溯源"
1 分钟架构画图讲：Vue → FastAPI（routers→services→db）→ SQLite + DeepSeek
3 分钟功能新建→Markdown→保存→搜索→标签筛选→AI 摘要→AI 建议标签
2 分钟问答选 2 篇提问，展示 [1] 角标 → 来源卡片 → 打开笔记核对
1.5 分钟工程pytest 全绿、Git 提交记录、Prompt 日志、Debug 记录

微任务卡（M1 · 演练卡 · L4）：把演示脚本发给 AI："请按 8 分钟限时检查这个脚本：哪一步最容易超时？演示顺序是否先价值后细节？给出 3 条压缩建议。"按建议演练一遍。

04. 35.4 任务二：架构讲解话术 ▼

35.4.1 一分钟版

"前端是 Vue 的三栏工作区：左边笔记库、中间编辑/问答、右边 AI 助手。请求走 REST 到 FastAPI 后端，后端分三层：路由只做参数校验，业务和 AI 调用在 services，SQL 全部在 db 层。数据存在本地 SQLite，AI 走 DeepSeek API。这样分层的好处是：AI 调用可以整体替换成假的来测试，数据库换库也只动一层。"

35.4.2 必答的三个取舍

  1. 为什么多对多中间表：一篇笔记多标签、一个标签多笔记，note_tags 是唯一正确建模；
  2. 为什么不做向量检索：9 学时、刚学完基础，问答用"选定笔记 + 正文截断"，引用用"关键词回查原文"，零额外依赖、可解释、成本可控——是规模与质量的取舍；
  3. 为什么 API Key 不写代码里：写进去等于把账号密码贴 GitHub 上；.env + .gitignore 是第一道防线，验收红线。

05. 35.5 任务三：Code Review 复盘 ▼

统计并回答（写进复盘文档）：

  1. 你们建了几个 feature 分支？PR 平均多久被 Review？
  2. Review 抓到过哪些真 Bug？（例：update 返回布尔值、204 无 body 解析失败）
  3. 有没有"Review 时发现问题但急着合"的时刻？后来付出什么代价？
  4. 哪些让 AI 做了、哪些必须自己做——这是 L4 复盘的核心：
    • 让 AI 做：代码骨架、测试用例、README、报错解释、方案对比；
    • 必须自己做：架构决策、需求取舍、验收判断、Key 安全、最终 Review。

判断标准：你能向队友讲清楚的代码才算你的。

微任务卡（M2 · 复盘卡 · L4）：把 Git 提交记录发给 AI："请分析我们的提交记录：commit message 是否规范？有没有'一个大提交塞了 20 个文件'的问题？给出改进建议。"把建议写进复盘。

07. 35.7 任务五：简历项目包装（STAR） ▼

35.7.1 STAR 模板

项目名称：AI 学习笔记助手（全栈 + AI，2-3 人小组）
S（背景）：14 天脱产培训综合实战，9 学时完成，团队 2-3 人
T（任务）：交付可演示的 AI 笔记应用：笔记 CRUD、标签、全文搜索、
          AI 摘要、基于笔记的问答（引用可溯源）
A（行动）：
· 契约先行：冻结 15 个 REST 接口，前后端并行开发
  · 三层架构：routers→services→db，AI 调用封装为可替换服务
  · 工程保障：pytest 24 条用例（假 AI 注入，不依赖真实 API）
  · 全程 Vibe Coding：Prompt 日志 8 份，Review 采纳/否决有据
R（结果）：测试全绿；两条命令本地部署；答辩演示通过；
          沉淀需求/设计/验收/协作全套文档

35.7.2 面试追问清单（提前准备）

  1. 搜索为什么用 LIKE 而不是 FTS5？（答：数据量小够用 + 成本取舍；FTS5 是扩展方向）
  2. AI 回答的引用是怎么实现的？（答：关键词回查段落，回答只保留标注的引用）
  3. 如果 10 万条笔记怎么办？（答：FTS5 / 分页 / 索引）
  4. 你的项目有什么缺点？（答：单用户无鉴权、问答不是流式、无向量检索——并说出改进方案）
  5. 讲一个你 Review 后否决 AI 建议的例子。
