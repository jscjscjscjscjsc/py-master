02. 15.1 软件工程导论 ▼

15.1.1 概念认知：软件危机与软件工程

20 世纪 60-70 年代，软件规模快速膨胀，出现了著名的软件危机：

  • 项目严重超期、超预算；
  • 交付的软件 bug 多、难以维护；
  • 程序员写的代码只有自己能看懂，一离职就"人亡政息"。

1968 年 NATO 会议正式提出"软件工程"这个词，定义沿用至今：用系统化、规范化、可度量的工程方法来开发、运行和维护软件。

一句话理解：写代码是"手艺活"，软件工程是把"手艺活"变成"工程活"——有流程、有规范、可度量、可协作。你前 8 天学的函数拆分、模块组织、Git 提交，全是软件工程的具体体现，今天开始把它们串成体系。

先定义清楚：软件是什么？

  • 程序 = 数据 + 指令：软件本质是按特定顺序组织的数据与指令的集合；
  • 程序 = 数据结构 + 算法（程序设计领域的经典表达）：数据结构管"数据怎么组织"，算法管"怎么处理"——你学的列表/字典是数据结构，查找/排序是算法。

软件分两类：

  • 系统软件：管理计算机底层硬件、提供操作界面（Windows、Android、macOS）；
  • 应用软件：处理某一领域的具体问题（微信、Excel、游戏）。

就业提示：面试问"什么是软件"，答"按特定顺序组织的数据与指令的集合"是标准定义；补"程序 = 数据结构 + 算法"是加分项。

15.1.2 语法掌握：软件生命周期

一个软件从无到有再到退役，经历六个阶段：

需求分析 → 设计 → 编码 → 测试 → 部署 → 维护
阶段干什么产出物你已接触过
需求分析搞清"做什么"需求文档第 14 章通讯录需求
设计规划"怎么做"架构/模块设计第 7 章函数拆分
编码写代码代码Day 1-8 全部
测试验证对不对测试用例第 17 章即将学习
部署让用户用上运行环境第 30 章项目部署
维护修 bug、加需求新版本Git 提交记录

每个阶段谁负责？——岗位角色一览（就业认知）

阶段岗位干什么
需求分析产品经理 / 项目经理收集需求、定义功能边界、排优先级、定计划
设计系统架构师 / 数据库工程师 / UI 设计师技术选型与分层架构、数据表设计、界面原型
开发前端 / 后端 / 移动端工程师写页面、写业务逻辑与 API、对接第三方
测试测试工程师验证功能正确性、覆盖范围
部署与运维运维 / 网络 / 安全工程师配置环境、监控运行、保护数据与设备

讲解："开发"只是六分之一，每个岗位都是一条就业路径——你学 Python 打底，之后可以向后端、测试、运维、数据分析等方向分化。

微任务卡（M1 · 讲解卡 · L2）：把岗位角色表发给 AI："请结合我的 Python 学习路径，说明我最可能先匹配哪个岗位、还需要补什么技能。"一句话记录结论。

交叉验证：大部分"程序员"卡在哪？

❌ 新手误区：只会"编码"这一个阶段，觉得写代码就是全部。

✅ 工程视角：编码只是六分之一。真实项目里，需求理解、测试、维护的时间加起来远多于"敲键盘"的时间——这就是为什么企业招人看重"工程素养"而非单纯的手速。

案例 15.1：用生命周期审视你自己的项目（Day 14 的"迷你通讯录"）

需求分析：谁用？自己。场景？记联系人。核心功能？增删查列（4 条）；
设计：函数拆分（load/add/find/delete/main）+ 数据格式（JSON 字典列表）；
编码：写代码（你做过的那部分）；
测试：输入不同数据手动跑，确认增删查不出错；
部署：把它变成一个双击可运行的工具（打包 .exe，第 30 章项目再学）；
维护：新增"按电话查找"——回到需求分析，走一遍新迭代。

讲解：一个小项目也能完整走六阶段——你不是没有工程流程，而是没意识到自己一直在走。把"下意识"变成"有意识"，就是工程素养的开始。

15.1.3 语法掌握：瀑布 vs 敏捷

瀑布模型（Waterfall）：严格按 需求→设计→编码→测试→部署 顺序走，上一阶段完成才进下一阶段。像瀑布，只能往下流，不能回头。

敏捷开发（Agile）：把项目切成 2-4 周一个的迭代（Sprint），每个迭代都交付一个可运行的小版本，边做边根据反馈调整。

维度瀑布敏捷
需求前期全部定死迭代中持续调整
交付最后一次性交付每个迭代交付可用版本
变更代价大（要回退）拥抱变更（下一迭代做）
适合需求稳定、监管严格（如银行核心）需求变化快（Web/App/创业）

原理探秘：为什么 Vibe Coding 和敏捷是"天生一对"？

回顾 Vibe Coding 的核心闭环：需求表达 → 原型生成 → 直觉校验 → 反馈迭代——这本质上就是一个"微型敏捷迭代"：

敏捷 Sprint：需求 → 开发 → 评审 → 下一个 Sprint
Vibe 闭环：  描述需求 → AI 生成 → 你验证 → 再描述

两者共享同一个底层哲学：不确定性不可怕，快速反馈才是解药。这也是为什么"AI 时代程序员必须懂敏捷"——你不是在学一个新概念，而是在理解自己每天在做的事。

15.1.4 原理探秘：需求错误的代价最贵

软件工程经典研究（常引 IBM 等公司的数据）表明：缺陷发现得越晚，修复成本越高——

缺陷在哪个阶段被发现相对修复成本
需求阶段1
设计阶段3-6
编码阶段10
测试阶段15-40
上线后100 倍以上

数据来源：缺陷成本随发现阶段上升的结论是软件工程经典研究（常引 IBM 与 Barry Boehm 的研究），具体倍数因项目而异——"越晚修越贵"的趋势是行业共识，数字是量级参考。

含义：需求理解错了，编码阶段才发现 = 重写；上线后才发现 = 用户流失 + 紧急修复 + 信任受损。所以需求分析是软件工程最重要的阶段——"想清楚再动手"永远比"边写边改"便宜。

就业提示：面试官问"为什么需求分析重要"，用这条成本曲线回答，立刻显得专业。

03. 15.2 需求分析：把"想法"变成"需求文档" ▼

15.2.1 概念认知：需求四要素

任何需求，先想清楚四件事（第 2 章原教材的"用户/场景/价值/核心功能"）：

  1. 用户：谁用？（学生？老师？店主？）
  2. 场景：在什么情况下用？（上课签到？晚上记账？）
  3. 价值：解决什么痛点？（省时间？防出错？）
  4. 核心功能：必须有哪几个功能？（不是"想要的所有功能"）

代码案例 15.2：模糊需求 vs 明确需求（❌ vs ✅）

❌ 模糊需求："我想做一个打卡系统。"

✅ 明确需求：

用户：培训机构的班主任；
场景：每天课前，学生用手机签到；
价值：替代纸质点名，自动统计出勤率，省 20 分钟/天；
核心功能：① 学生输入学号签到 ② 记录签到时间 ③ 生成出勤报表。

交叉验证：为什么模糊需求会"做错"？

❌ 模糊的后果：程序员按自己的理解做了"指纹打卡 + 人脸识别 + 请假审批"——功能多但都不是老师要的，还延期两个月。

✅ 明确的收益：双方对"做什么"达成共识，开发只围绕三个核心功能，验收时有标准。

讲解："明确"不是要求一次性写完美，而是把"谁、什么场景、解决什么、哪些功能必须有"说清楚——剩下的细节可以在迭代中补充（敏捷思想）。

15.2.2 语法掌握：需求文档的六段结构

一份可用的需求文档（一页纸版）包含六段：

一、项目背景：为什么做？
二、项目目标：做成什么样算成功？
三、功能需求：有哪些功能？（核心功能 + 每条验收标准）
四、技术需求：用什么技术栈？（Python 版本、文件格式、运行环境）
五、界面需求：长什么样？（命令行菜单 / 页面布局）
六、验收标准：满足什么条件才算交付？

代码案例 15.3：待办清单工具的需求文档（✅ 示例）

markdown
# 待办清单工具 需求文档

## 一、项目背景
班级同学常忘记作业和小任务，需要一个简单的本地待办工具。

## 二、项目目标
命令行即可使用，任务数据重启后不丢失。

## 三、功能需求
1. 添加任务（内容 + 截止日期）；
2. 查看所有任务（未完成在前）；
3. 标记任务为已完成；
4. 删除任务。
验收：以上 4 个功能在命令行操作流畅、无崩溃。

## 四、技术需求
- Python 3.12+，命令行运行；
- 数据存 JSON 文件（tasks.json）；
- 不使用任何第三方库。

## 五、界面需求
菜单式交互，共 5 个选项（1 添加 / 2 查看 / 3 完成 / 4 删除 / 5 退出）。

## 六、验收标准
1. 添加 3 个任务后重启程序，任务仍在；
2. 标记完成后，任务出现在"已完成"区；
3. 输入非法选项有提示、不崩溃。

讲解：这份文档只有一页，但"做什么、怎么验收"全部说清——程序员照它写代码不会跑偏，验收时照它逐条核对。这就是需求文档的价值。

扩展：功能需求之外，还有"非功能需求"

六段结构主要写功能需求（系统做什么）。别忘了非功能需求（系统做得怎么样）：

类型例子
性能列表加载不超过 1 秒、支持 1000 条数据
安全数据文件权限、输入校验、密钥不硬编码
可用性操作步骤不超过 3 步、错误提示可理解

就业提示：面试问"你写过非功能需求吗"，能说出"性能/安全/可用性"三类 + 一个例子，就比只说功能需求强。

扩展：用户故事（User Story）——敏捷的需求表达

敏捷团队常用一句话表达需求：

作为【用户】，我想要【功能】，以便【价值】。

示例："作为学生，我想要看到作业的截止倒计时，以便不忘记交作业。"

讲解：用户故事 = 需求四要素的口语版（用户/功能/价值）——和四要素一一对应。面试或工作中听到"写个 user story"，就是这套格式。

15.2.3 综合运用：Vibe 需求工作流（L2）

需求文档不该让 AI 代写内容（那是你的业务判断），但可以让 AI 当"框架整理器"：

微任务卡（M2 · 对比卡 · L2）：把上面"模糊 vs 明确"两份需求发给 AI，提问："请对比这两份需求的差异，指出模糊需求会导致哪些开发风险。"一句话记录结论。

步骤：

  1. 描述想法：用一两句话告诉 AI"我想做一个 X 工具，给 Y 用，解决 Z"；
  2. AI 生成框架（L2 允许）：让 AI 输出"需求文档的六段骨架和每个字段的提问清单"——只要结构，不要内容；
  3. 人工填写：你自己回答"用户是谁、核心功能有哪些"——业务判断必须是你做的；
  4. 小组互评：互相看对方的需求文档，按四要素检查有没有漏洞；
  5. 定稿入库：git add + commit，需求文档进仓库（Git 记录版本，需求变更有迹可循）。

微任务卡（M3 · 讲解卡 · L2）：把 AI 生成的"提问清单"发给 AI："请解释为什么'核心功能'要克制、'验收标准'必须可测试？"一句话记录理解。

红线提醒（L2）：让 AI"帮我写需求文档"= 让它生成内容 = 越界。AI 只能做框架和提问，答案必须来自你对业务的理解——这是 L2 的判别标准：AI 输出的是"结构/建议"还是"替你做的决定"。

04. 15.3 本章 Debug 四件套（需求阶段的坑） ▼

这四套没有代码，但都是真实项目里"返工事故"的源头。玩法不变：先自己想，再看讲解。

问题 1：需求模糊

问题描述："做一个图书管理系统。"

后果：程序员做成了"图书馆级"系统（馆藏、借阅、逾期罚款、统计报表），用户其实只想要一个"自己家的书单记录"——两个月白做。

提示：四要素里缺了什么？用户是谁、场景是什么？

讲解：没有用户、场景、价值，需求就无从收敛。先补四要素，再谈功能。

问题 2：范围蔓延（Scope Creep）

问题描述：开发中客户不断加需求："顺便加个导出 Excel""再做个手机版""最好能语音输入"……

后果：项目无限延期，核心功能都没做稳。

提示：需求变更是拒绝还是接受？有没有机制管理变更？

讲解：敏捷的做法不是"拒绝变更"，而是把变更排进下一个迭代，本迭代先保证核心功能交付。核心功能 = 底线，其余 = 可延后。

问题 3：没有验收标准

问题描述：需求文档写"界面美观、体验好"。

后果：你说完成了，用户说不行——"美观"无法度量，各说各话。

提示：验收标准应该怎么定义才可测试？

讲解：验收标准必须可验证：改成"所有按钮点击有响应""错误输入有提示不崩溃""数据重启后不丢失"这类能逐条打勾的描述。

问题 4：技术需求缺失

问题描述：需求文档只写功能，没写"Python 版本、数据格式、运行环境"。

后果：开发用 Python 3.13 的新特性，用户机器只有 3.10，跑不起来。

提示：六段结构里哪一段没写？

讲解：技术需求 = 开发的"地基契约"：Python 版本、依赖清单、文件格式、兼容性，必须在文档里写死（你 Day 5 学的 requirements.txt 就是它的落地形式）。

06. 15.5 本章小结与知识树 ▼

知识树：

软件工程导论与需求分析
├── 软件危机 → 软件工程：系统化/规范化/可度量
├── 生命周期：需求→设计→编码→测试→部署→维护（编码只是六分之一）
├── 开发模式
│   ├── 瀑布：顺序执行、需求定死、适合稳定场景
│   └── 敏捷：迭代交付、拥抱变更、与 Vibe Coding 闭环同构
├── 成本曲线：需求阶段发现的缺陷最便宜，上线后最贵（100 倍）
├── 需求四要素：用户 / 场景 / 价值 / 核心功能
├── 需求文档六段：背景 / 目标 / 功能 / 技术 / 界面 / 验收
│   └── 验收标准必须可测试（能打勾）
└── Vibe 需求工作流：想法 → AI 生成框架（不给内容）→ 人工填写 → 互评 → 入库

必须记住的 5 件事：

  1. 编码只是软件生命周期的六分之一；
  2. 需求阶段修缺陷最便宜，上线后最贵（约 100 倍）；
  3. 需求四要素：用户、场景、价值、核心功能；
  4. 验收标准必须可测试——"美观""好用"不算标准；
  5. AI 只做需求框架，业务判断永远是你自己做的。

07. 本章速查 ▼
术语一句话
软件定义程序 = 数据 + 指令；程序 = 数据结构 + 算法
软件分类系统软件（Windows）/ 应用软件（微信、Excel）
岗位角色需求→产品/项目经理；设计→架构师/DB/UI；开发→前端/后端；测试→测试工程师；运维→运维/网络/安全
生命周期需求→设计→编码→测试→部署→维护
瀑布 vs 敏捷顺序定死 vs 迭代交付
需求四要素用户 / 场景 / 价值 / 核心功能
需求文档六段背景 / 目标 / 功能 / 技术 / 界面 / 验收

非功能需求性能 / 安全 / 可用性
范围蔓延变更排进下一迭代，不挤占本迭代
